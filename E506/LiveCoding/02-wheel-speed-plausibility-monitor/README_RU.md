# Упражнение 2: Монитор достоверности двух датчиков скорости колеса

## Цель

Реализовать циклический state machine, который сравнивает основной и резервный входы скорости колеса и выдаёт состояние `Available` или `Degraded`.

## Бизнес-контекст и назначение

Функции автомобиля могут использовать данные о скорости колеса для принятия решений или информирования водителя. Если измерение отсутствует, устарело или расходится с другим измерением той же величины, потребителю нужно понимать, можно ли по-прежнему полагаться на эти данные. Иначе функция может продолжить работу с недостоверной информацией или отключиться без необходимости.

В упражнении моделируется небольшой монитор доступности для двух сопоставимых измерений скорости одного и того же колеса. Он проверяет качество и согласованность данных и сообщает использующему их компоненту статус `Available` или `Degraded`. Например, отсутствие sample сразу вызывает деградацию; краткое расхождение допускается, а три последовательных расхождения приводят к деградации. Для восстановления требуются пять последовательных правдоподобных циклов. Это согласованные значения упражнения, а не универсальные требования для автомобилей.

Для продуктовой команды потенциальная польза — понятный контракт между данными сенсоров и их потребителями: отказы становятся заметны, кратковременные расхождения с меньшей вероятностью вызовут повторные изменения состояния, а диагностика поможет расследовать проблему. Компонент может поддерживать решения о доступности функции и обслуживании, но упражнение не подтверждает конкретную экономию, долю обнаруженных отказов или результат для безопасности автомобиля.

Монитор не определяет, какой сенсор прав, не выдаёт достоверную оценку скорости, не ремонтирует датчик и не решает, как должны реагировать торможение, система стабилизации или приборная панель. Его результат полезен только тогда, когда для потребляющей функции определена реакция на оба статуса. Согласованность сама по себе не доказывает точность: оба сенсора могут иметь общую ошибку. В реальном продукте архитектуру сенсоров, условия эксплуатации, реакцию на отказ и пороги нужно определить и проверить на системном уровне.

Для собеседования задача полезна тем, что компактная бизнес-проблема приводит к конкретным инженерным решениям: валидации входов, проверке свежести, счётчикам последовательных циклов, восстановлению, диагностике, правилам публикации и тестам. Само упражнение не присваивает монитору ASIL: он зависит от реальной функции автомобиля, опасности и распределённых требований безопасности.

## Шаг 1: Задать вопросы до кодирования

- Каковы единицы и физический диапазон?
- Каково максимальное допустимое расхождение?
- Включается ли точное значение порога?
- Сколько плохих циклов вызывает деградацию?
- Сколько хороших циклов требуется для восстановления?
- Приводит ли отсутствие одного сенсора к немедленной деградации?
- Когда данные считаются stale?
- Нужно ли подавлять повторные status notifications?
- Какая функция автомобиля использует результат?

## Шаг 2: Согласованные требования

- REQ-WSP-001: `tick()` вызывается каждые 20 ms.
- REQ-WSP-002: Допустимый включительный диапазон значений — 0,0–100,0 m/s.
- REQ-WSP-003: Sample старше 50 ms считается stale.
- REQ-WSP-004: Расхождение не более 1,5 m/s считается допустимым.
- REQ-WSP-005: Три последовательных недопустимых цикла переводят компонент в `Degraded`.
- REQ-WSP-006: Один допустимый цикл сбрасывает bad-cycle counter до деградации.
- REQ-WSP-007: Отсутствующие, stale или non-finite данные немедленно переводят компонент в `Degraded`.
- REQ-WSP-008: Пять последовательных допустимых циклов восстанавливают `Available`.
- REQ-WSP-009: Status отправляется только при изменении наблюдаемого состояния.

## Шаг 3: Определить mocks

- Primary sensor port.
- Secondary sensor port.
- Monotonic clock.
- Status output port.
- Diagnostic sink.

## Шаг 4: Построить матрицу тестов

1. Равные допустимые значения сохраняют `Available`.
2. Расхождение ровно 1,5 m/s остаётся допустимым.
3. Расхождение непосредственно выше порога в течение одного и двух циклов сохраняет `Available`.
4. Третий последовательный плохой цикл переводит в `Degraded`.
5. Допустимый цикл сбрасывает bad counter.
6. Отсутствие primary или secondary input немедленно переводит в degraded.
7. Sample возрастом 50 ms принимается, 51 ms считается stale.
8. NaN, infinity, отрицательные и выходящие за диапазон значения немедленно переводят в degraded.
9. Восстановление происходит на пятом последовательном допустимом цикле, а не на четвёртом.
10. Пока состояние не меняется, повторный output не отправляется.

## Шаг 5: Реализовать явно

- Валидировать каждый input до сравнения значений.
- Хранить bad и recovery counters отдельно.
- Централизовать переход состояния и notification.
- Обновлять counters только после классификации цикла.
- Не обращаться к скрытому wall clock.

## Шаг 6: Замкнуть V-model

- Unit tests проверяют counters, thresholds и transitions.
- Integration tests должны проверить реальные sensor messages и преобразование timestamps.
- Target tests должны проверить scheduler jitter и timing обновлений сенсоров.
- Vehicle-level validation зависит от потребителя speed estimate.

## Вопрос по ASIL

Нельзя классифицировать monitor до определения его потребителя. Display-only speed, вход braking и вход stability control создают разные hazardous events. Нужно запросить item, эксплуатационную ситуацию и предположения S, E и C.

## Критерии готовности

- Проходят десять сценариев.
- State changes детерминированы.
- Время инъецировано.
- Invalid data никогда не считается допустимым.
- Нет повторного status side effect.
