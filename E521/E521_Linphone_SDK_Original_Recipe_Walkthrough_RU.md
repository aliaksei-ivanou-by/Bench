LINPHONE SDK: ПОСТРОЧНЫЙ РАЗБОР ОРИГИНАЛЬНОГО РЕЦЕПТА YOCTO

01. КАК ЧИТАТЬ РАЗБОР

Это руководство по чтению предоставленного снимка, а не новый рецепт и не доказательство конфигурации исторического выпуска. Отдельное руководство с примером реализации объясняет полный процесс интеграции. Здесь разобрана каждая физическая строка: R001–R273 для рецепта, C001–C171 для локального класса CMake и L001–L011 для layer.conf. В двух языковых версиях одинаковые идентификаторы и выдержки исходников.

Корень локального слоя — C:\Users\User\Downloads\meta-bc\meta-bc. Файлы просмотрены без изменений. В выдержках сохранена нумерация физических строк; табуляция показана пробелами, концевые пробелы убраны. Только в R071 закрытый адрес Git заменён на private-host/private-repository.git. Это цитата со скрытым адресом, а не готовая настройка загрузки.

Сначала читаем блок исходника, затем объяснения строк. Продолжения и скобки являются частями целых конструкций, а не отдельными командами для вставки. Удаление и перемещение в классе показаны как разбираемый исходник; при проверке они не выполнялись. Полная сборка Yocto и запуск на устройстве не проводились.

02. ОСНОВНАЯ ЛОГИКА

Сборочные зависимости предоставляют заголовки, библиотеки и инструменты хоста. Toolchain выбирает архитектуру телефона. CMake собирает SDK, do_install устанавливает файлы внутрь D, FILES распределяет их по пакетам, а образ выбирает рабочие пакеты. Выбор исходников, строка версии и версия для пакетного менеджера — разные механизмы. RPROVIDES не создаёт рецепты исходников; SYSROOT_DIRS не настраивает загрузчик телефона; успешная компиляция не доказывает работу звонков.

Используемые пути: WORKDIR — рабочий каталог рецепта; S — распакованные исходники; B — результаты сборки; D — временный корень установки; RECIPE_SYSROOT — зависимости. BUILD_INSTALL_PATH — промежуточное дерево SDK этого рецепта; INSTALL_PATH_OUT — итоговое расположение /opt на устройстве. Пути хоста сборки не должны становиться путями поиска библиотек на устройстве.

R001–R012. ОПИСАНИЕ И НАЧАЛЬНЫЕ ЗНАЧЕНИЯ

```bitbake
VERSION_DEPENDENT_DEPENDS=""
VERSION_DEPENDENT_INHERIT="python3native"
```

- R001: Объявляет пустую добавку для сборочных зависимостей конкретной версии. R019 вставляет её в DEPENDS; сейчас новых зависимостей она не добавляет.

- R002: Выбирает python3native как наследуемый класс для этой версии. Он подготавливает Python для скриптов сборки на хосте, а не устанавливает Python на телефон.

- R003: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R004: Комментарий описывает резервный commit, но следующая строка не задаёт фиксированную ревизию: там AUTOREV. В этом случае ориентируемся на действующие настройки, а не на комментарий.

- R005: Задаёт резервную ревизию через механизм AUTOREV. Без явного закрепления исходники могут меняться между сборками при неизменном тексте рецепта.

- R006: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R007: Задаёт текстовое описание пакета. WIP и console edition — подписи в этом снимке; они не определяют, будет ли у собранного продукта интерфейс.

- R008: Задаёт информационную страницу проекта. Это не адрес загрузки исходников: загрузкой управляет SRC_URI.

- R009: Относит пакет к категории network. SECTION — метаданные, а не зависимость сборки и не настройка сети.

- R010: Задаёт SECTION для контекста linphonec. Правило действует только при соответствующем override или обработке пакета и не создаёт пакет linphonec.

- R011: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R012: Задаёт собственный префикс ревизии, используемый в R271. INC_PR — переменная этого рецепта, а не отдельная задача.

R049–R071. ВЫБОР РЕВИЗИИ И ЗАГРУЗКА

```bitbake

python () {
# 3 possible revisions:
# - if env[LATEST_REVISIONS] is set, use yocto autorev mecanism
# - if env[LINPHONE_SDK_REV] is defined, use the value as the revision (useful for continous integration)
# - Otherwise, use fixed stable revision

    if os.getenv('LATEST_REVISIONS', '') == "1":
        d.setVar('SRCREV', "${AUTOREV}")
    else:
        d.setVar('SRCREV', os.getenv('LINPHONE_SDK_REV', "${DEFAULT_COMMIT}"))

    d.setVar('LINPHONE_SDK_BRANCH', os.getenv('LINPHONE_SDK_BRANCH', 'master'))
}

# For visualisation
python () {
    print("")
    print("linphone-sdk")
    print(d.getVar('SRCREV', True))
}

SRC_URI = "gitsm://private-host/private-repository.git;protocol=http;branch=main"
```

- R049: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R050: Начинает анонимный Python, выполняемый при подготовке метаданных, а не shell-задачу do_compile. Он меняет datastore рецепта.

- R051: Вводит три задуманных режима выбора исходников. Реальное поведение задают R056–R061.

- R052: Описывает режим AUTOREV. Реализация требует именно строку 1, а не любое непустое значение.

- R053: Описывает явный commit из окружения. BitBake должен пропускать эту переменную в своё окружение, иначе обработчик её не прочитает.

- R054: Утверждает, что резервная ревизия фиксированная, но R005 задаёт AUTOREV. Комментарий не соответствует этому снимку.

- R055: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R056: Читает LATEST_REVISIONS из окружения процесса и сравнивает с 1. Это os.getenv, а не прямое чтение переменной datastore из local.conf.

- R057: При включённом переключателе задаёт SRCREV через AUTOREV. Тем самым допускается изменение исходников между сборками.

- R058: Начинает другую ветку, когда переключатель последней ревизии не включён.

- R059: Берёт LINPHONE_SDK_REV при наличии, иначе DEFAULT_COMMIT. Поскольку там AUTOREV, одного отключения LATEST_REVISIONS недостаточно для повторяемой сборки.

- R060: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R061: Сохраняет имя ветки из окружения, по умолчанию master. R071 эту переменную не использует, поэтому данное присваивание само не меняет загружаемую ветку main.

- R062: Завершает анонимный блок Python. Здесь определяются метаданные, а не запускается сервис устройства.

- R063: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R064: Вводит диагностический вывод при разборе метаданных. Это не настройка логирования устройства.

- R065: Начинает ещё один анонимный Python. При разборе в разных контекстах он может повторно печатать сообщения.

- R066: Печатает пустую строку между диагностическими сообщениями. Переменные не меняет.

- R067: Печатает имя рецепта. Структурированный bb.note удобнее контролировать, чем безусловный print.

- R068: Печатает раскрытый SRCREV. Определение AUTOREV может требовать доступа к репозиторию; вывод является диагностикой, а не надёжным manifest выпуска.

- R069: Закрывает диагностический блок Python.

- R070: Пустая строка-разделитель. Она не меняет переменные и не добавляет задачу.

- R071: Получает закрытые исходники Git с подмодулями по HTTP из буквальной ветки main. Сервер и путь в показанной строке скрыты. gitsm использует записанные ссылки на подмодули и не означает автоматический выбор их последних веток.

```bitbake
    eval ${DESTDIR:+DESTDIR=${DESTDIR} }VERBOSE=1 cmake --build '${B}' "$@" -- ${EXTRA_OECMAKE_BUILD}
}

cmakebuilder_do_compile()  {
    cmake_runcmake_build --target ${OECMAKE_TARGET_COMPILE}
}

EXPORT_FUNCTIONS do_configure do_compile do_generate_toolchain_file
```

06. КАК СВЯЗАНЫ НАСЛЕДУЕМЫЕ КЛАССЫ

Локальный cmakebuilder — не вся система сборки. cmake_qt5 наследует cmake и qmake5_paths. Другие классы добавляют gettext, pkg-config, Perl/Python, инструменты работы с путями библиотек и версии пакетов из Git. Само наличие cmakebuilder_do_configure ещё не доказывает, что итоговая do_configure использует её. Проверяем раскрытые тела задач и историю метаданных; после выполнения задач смотрим также сформированные run.do_* скрипты.

Для точного исторического поведения нужны версии классов из исходной сборки продукта. Официальный cmake_qt5 для Kirkstone подтверждает наследование стандартного cmake, но не доказывает использование продуктом именно этой ревизии. Если снимок не проходит разбор из-за старых overrides, сначала исправляем их в рабочей копии, а затем используем bitbake -e.

07. КОМАНДЫ ДЛЯ ПРОВЕРКИ ОБЪЯСНЕНИЙ

Команды выполняются из существующего окружения сборки телефона с его BSP и слоем Qt. Полные раскрытые метаданные оставляем локально: в них могут быть закрытые URL и пути. Это команды просмотра, кроме явно указанных задач сборки.

```bash

bitbake-layers show-layers
bitbake-layers show-recipes linphone-sdk
bitbake-layers show-appends
bitbake -e linphone-sdk > linphone-sdk.environment.txt

grep -E '^(FILE|SRCREV|PV|PR|PKGV|S|B|D|T|RECIPE_SYSROOT|BUILD_INSTALL_PATH|INSTALL_PATH_OUT)=' \
    linphone-sdk.environment.txt

    linphone-sdk.environment.txt

sed -n '/^do_configure()/,/^}/p' linphone-sdk.environment.txt
sed -n '/^do_compile()/,/^}/p' linphone-sdk.environment.txt
sed -n '/^do_install()/,/^}/p' linphone-sdk.environment.txt
bitbake -c listtasks linphone-sdk
```

Для проверки реальной установки и упаковки сначала выбираем согласованную фиксированную ревизию и выполняем нужные этапы. При ошибке читаем лог, а не предполагаем наличие результатов следующего этапа. Завершение do_install ещё не создаёт packages-split: оно появляется при упаковке.

```bash

bitbake -c install linphone-sdk
bitbake linphone-sdk

oe-pkgdata-util list-pkgs 'linphone-sdk*'
oe-pkgdata-util list-pkg-files linphone-sdk
oe-pkgdata-util list-pkg-files linphone-sdk-dev
oe-pkgdata-util find-path /etc/ld.so.conf.d/belledonne.conf

# Re-read the environment if any build configuration changed.
bitbake -e linphone-sdk > linphone-sdk.environment.txt
sdk_logs=$(sed -n 's/^T="\(.*\)"$/\1/p' linphone-sdk.environment.txt)
sdk_work=$(sed -n 's/^WORKDIR="\(.*\)"$/\1/p' linphone-sdk.environment.txt)
find "$sdk_logs" -maxdepth 1 -name 'log.do_*' -print
find "$sdk_logs" -maxdepth 1 -name 'run.do_*' -print
find "$sdk_work/packages-split" -name 'liblinphone.so*' -print
find "$sdk_work/packages-split" -name '*.pc' -print
```

09. КРАТКОЕ ОБЪЯСНЕНИЕ ДЛЯ СОБЕСЕДОВАНИЯ
