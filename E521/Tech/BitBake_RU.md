BitBake

РАЗДЕЛ 1. ТЕХНОЛОГИЯ И ВЕРСИЯ

Категория: Инструмент сборки

BitBake 2.0 с Yocto Kirkstone; точное поведение зависит от версии проекта.

РАЗДЕЛ 2. НАЗНАЧЕНИЕ

BitBake читает инструкции сборки и выполняет задачи в порядке зависимостей. Это исполнитель сборки OpenEmbedded. Рецепты, классы и конфигурация определяют его работу.

РАЗДЕЛ 3. ОСНОВНЫЕ ПОНЯТИЯ

- BitBake объединяет настройки, классы, рецепты и подходящие .bbappend, затем выбирает рецепты и версии компонентов.
- Обычные задачи загружают и распаковывают исходники, применяют патчи, настраивают и компилируют проект, устанавливают и упаковывают результат.
- Зависимости связывают задачи разных рецептов. DEPENDS задаёт рецепты для сборки, RDEPENDS — пакеты для работы на устройстве.
- У задачи есть сигнатура, рассчитанная по важным входным данным и настройкам. Подходящий результат sstate позволяет не выполнять работу повторно.
- Если зависимость не описана, BitBake может повторно использовать неверный результат. Очистка кеша не исправляет описание зависимости.
- do_install пишет во временную область. Упаковка и создание образа идут позже. Поэтому отсутствие библиотеки на устройстве и ошибка configure требуют разных проверок.
- Несколько слоёв могут менять одну настройку. Проверяйте итоговое значение, а не только отдельное присваивание.

РАЗДЕЛ 4. ТИПИЧНОЕ ИСПОЛЬЗОВАНИЕ

Команды выполняются в инициализированной среде сборки.

- bitbake <recipe> собирает цель.
- bitbake <recipe> -c listtasks перечисляет задачи.
- bitbake -e <recipe> показывает раскрытое окружение.
- bitbake -g <target> создаёт графы зависимостей.
- bitbake-layers show-appends помогает найти применённые appends.

При ошибке задачи изучают log.do_* в рабочем каталоге рецепта.

При ошибке сборки определите рецепт и задачу, прочитайте её лог, затем проверьте итоговые метаданные и объявленные зависимости. Если сборка успешна, а файла нет на устройстве, проследите путь от do_install до содержимого пакета и выбора в образ, не пересобирая всё случайным образом.

Имена рецептов в DEPENDS и имена пакетов в RDEPENDS имеют разные роли. oe-pkgdata-util проверяет метаданные уже собранных пакетов текущей конфигурации.

СОЗДАНИЕ И ДИАГНОСТИКА РЕЦЕПТА

.bb описывает компонент; подходящий .bbappend расширяет его из другого слоя. Honister 3.4 ввёл overrides с двоеточием: SRC_URI:append = " file://fix.patch" и FILES:${PN}:append = " ${datadir}/phone". Для :append сохраняются необходимые пробелы. Нельзя заменять все подчёркивания: PREFERRED_VERSION_recipe и суффиксы коллекций слоёв не являются override-синтаксисом.

Использовать inherit cmake, meson или autotools согласно системе сборки. inherit pkgconfig интегрирует pkg-config для кросс-сборки, но не устанавливает зависимости и не заменяет DEPENDS.

Библиотеки устанавливаются в ${D}${libdir}, headers — в ${D}${includedir}, executables — в ${D}${bindir}. Стандартное разбиение обычно относит headers и development metadata в ${PN}-dev, отделённую debug information — в ${PN}-dbg.

FILES:${PN} использует целевые пути без ${D}; проверяются PACKAGES и реальные файлы вместо помещения всего в runtime.

Например, bitbake -e hello | grep '^PACKAGECONFIG=' показывает итоговое значение; для других задач меняется имя переменной. bitbake -c devshell hello открывает shell окружения сборки, а не target shell. oe-pkgdata-util list-pkg-files hello и oe-pkgdata-util find-path /usr/bin/hello исследуют данные уже собранных пакетов. bitbake-layers show-appends подтверждает применение appends.

devtool add добавляет новый компонент; devtool modify предоставляет исходники существующего рецепта; devtool build поддерживает итерации; devtool finish экспортирует зафиксированные изменения в сопровождаемый слой и снимает workspace override. Проверяются сгенерированные sources, license fields, dependencies и install behavior.

LICENSE определяет лицензии, LIC_FILES_CHKSUM отслеживает их текст, SRC_URI — входные данные fetch, SRCREV — фиксированную ревизию VCS. Изменение license checksum требует анализа текста, а не только принятия нового hash.

Для installed-vs-shipped проверяются ${D}, PACKAGES и FILES; нужные файлы относятся в корректный пакет, ненужные перестают устанавливаться. Для dev-so проверяются development symlinks; plugin .so могут требовать отдельного решения.

Для file-rdeps добавляется настоящий runtime-provider. Для buildpaths/rpaths из конфигурации убираются host-пути.

Глобальный INSANE_SKIP скрывает дефекты вместо исправления.

ПРИМЕРЫ КОМАНД НА LINUX-HOST

Проверка метаданных и состава пакетов для рецепта hello:

```bash
bitbake -e hello | grep '^PACKAGECONFIG='
bitbake-layers show-appends
oe-pkgdata-util list-pkg-files hello
oe-pkgdata-util find-path /usr/bin/hello
```

Отдельная интерактивная сессия окружения сборки:

```bash
bitbake -c devshell hello
```

ФРАГМЕНТЫ РЕЦЕПТА

Пример расширения рецепта; пути относятся к целевой системе:

```bitbake
SRC_URI:append = " file://fix.patch"
FILES:${PN}:append = " ${datadir}/phone"
```

Для проекта на CMake с использованием pkg-config:

```bitbake
inherit cmake pkgconfig
```

РАЗМЕР СБОРКИ SIP И ПРОВЕРКА RUNTIME

- Различаются установленные bytes, размер rootfs и runtime RSS/PSS. GCC -Os оптимизирует размер кода, но не гарантирует меньшую память звонков/медиа. Перед изменением проверяются реальный compiler и flags.
- PACKAGECONFIG выражает поддерживаемые рецептом features. Tests, codecs или plugins отключаются только с сохранением нужной функциональности. Соответствующие debug symbols сохраняются для target-диагностики.
- Проверяются выбранный ELF interpreter, NEEDED и пути runtime plugins; успешная упаковка не доказывает загрузку ABI-совместимой библиотеки. Target-compatible readelf исследует ELF metadata без выполнения ARM-бинарника.

РАЗДЕЛ 5. ПРЕИМУЩЕСТВА, ОГРАНИЧЕНИЯ И АЛЬТЕРНАТИВЫ

Граф задач явно задаёт зависимости, параллельное выполнение и повторное использование. Сложность создают взаимодействующие слои, overrides, сигнатуры и providers. Для одного host-приложения прямой CMake или Make часто проще, но он не заменяет составление образа и метаданные кросс-сборки, когда они нужны.

РАЗДЕЛ 6. ОШИБКИ И БЕЗОПАСНОСТЬ

Отсутствующий DEPENDS может дать сборку, работающую только благодаря случайному состоянию host или кеша. Пропущенная runtime-зависимость может оставить успешную сборку и неработающее устройство. Конфликты версий и providers, неприменённые .bbappend и незафиксированные загрузки нарушают воспроизводимость. До массовой очистки кеша изучайте сигнатуры и логи.

РАЗДЕЛ 8. ВОПРОСЫ НА ИНТЕРВЬЮ

ВОПРОС BB-01. Что делает BitBake?

Ответ: Он читает рецепты, классы и настройки. Затем выбирает нужные рецепты и строит порядок задач с учётом зависимостей. Задача запускается после своих зависимостей; подходящий результат из кеша можно использовать повторно.

Пример и проверка: Для приложения телефона компиляция должна дождаться нужных результатов сборки SDK. Независимые задачи могут идти параллельно. При пропавшем условии проверьте граф. Ручной порядок запуска не заменяет правильное описание зависимости.

ВОПРОС BB-02. Чем отличаются DEPENDS и RDEPENDS?

Ответ: DEPENDS перечисляет рецепты, нужные для сборки: их заголовки и библиотеки попадают в рабочее окружение рецепта. RDEPENDS перечисляет пакеты, нужные на устройстве. Имя рецепта не всегда совпадает с именем его выходного пакета.

Пример и проверка: Например, при сборке приложению нужны заголовки SDK, а телефону — пакеты рабочих библиотек. Генератор исходников запускается на сборочном компьютере. Для каждого компонента определите сторону использования. Это предотвращает отсутствие пакетов на телефоне и случайные библиотеки компьютера.

ВОПРОС BB-03. Как посмотреть итоговое значение переменной?

Ответ: В настроенном окружении выполните bitbake -e recipe. Посмотрите итоговое значение и историю его изменений. Учитывайте все подключённые слои и .bbappend, а не только один файл.

Пример и проверка: Если опция SDK не действует, найдите итоговое значение и посмотрите, какой рецепт, append или настройка его изменили. Проверьте выбранный рецепт и версию. Иначе изменение другой копии файла может выглядеть как ошибка системы сборки.

ВОПРОС BB-04. Где искать причину ошибки задачи?

Ответ: Начните с log.do_* нужной задачи. Файл run.do_* показывает команды, которые выполнял BitBake. Ищите первую содержательную ошибку: последнее сообщение make часто лишь сообщает о последствиях.

Пример и проверка: Последнее сообщение compiler или make часто скрывает более ранний отсутствующий заголовок или неудачную проверку. Читайте лог с первой важной ошибки и сохраняйте контекст команды. При необходимости повторите нужную задачу. Не начинайте с удаления доказательств и правок чужих рецептов.

ВОПРОС BB-05. Почему сборка проходит, а программа на устройстве не работает?

Ответ: На устройстве могут отсутствовать библиотека, конфигурация, права или нужный сервис. Проверьте содержимое образа и то, что действительно установлено. Повторная компиляция не исправит ошибку запуска, если причина находится в другом месте.

Пример и проверка: Если телефон не загружает Linphone, сравните требования программы с библиотеками образа. Проверьте имена, совместимость и пути plugins и данных. Библиотека в каталоге сборки не равна установленной на телефоне. До пересборки подтвердите фактический релиз устройства.

ВОПРОС BB-06. Чем do_install отличается от сборки образа?

Ответ: do_install кладёт файлы во временный каталог ${D}. Затем они распределяются по пакетам. do_rootfs собирает выбранные пакеты в корневую файловую систему, а следующие задачи создают образ для установки. Файл в ${D} ещё не означает файл на устройстве.

Пример и проверка: Возьмите один пропавший файл и проследите его из ${D} в пакет и затем в образ. Так находится этап потери. Заголовок может правильно относиться к -dev, а не рабочему пакету. Исправляйте распределение, а не помещайте все файлы в один пакет.

ВОПРОС BB-07. Что проверить перед очисткой кеша?

Ответ: Посмотрите логи, итоговые настройки, ревизии исходников и причины повторного использования задач. Неверная зависимость или выбранный рецепт останутся неверными после очистки. Сначала определите, какую конкретно гипотезу должна проверить пересборка.

Пример и проверка: Например, необъявленный вход может не изменить сигнатуру задачи. Очистка даст одну удачную сборку, но описание останется неверным. Найдите и объявите пропущенный вход. Затем проверьте нужную пересборку при его изменении без постоянного удаления всего кеша.

ВОПРОС BB-08. Каков обычный порядок задач рецепта?

Ответ: Загрузка, распаковка, патчи, настройка сборки, компиляция, установка и упаковка. Точный порядок определяется зависимостями и подключёнными классами. Образ собирается из пакетов позже; не все задачи нужно писать в рецепте вручную.

Пример и проверка: Для приложения телефона компиляция должна дождаться нужных результатов сборки SDK. Независимые задачи могут идти параллельно. При пропавшем условии проверьте граф. Ручной порядок запуска не заменяет правильное описание зависимости.

ВОПРОС BB-09. Что означают S, B, D и WORKDIR?

Ответ: S — каталог исходников, B — каталог сборки, D — временный каталог установки, WORKDIR — рабочий каталог рецепта. Они могут различаться. Используйте эти переменные, чтобы не записывать результаты в слой и не устанавливать файлы в систему сборочного компьютера.

Пример и проверка: При отдельной сборке CMake исходники остаются в S, результаты появляются в B. Установка помещает их в D для упаковки. Используйте эти переменные в задачах. Жёсткие пути могут записать файлы в слой или установить их на компьютер вместо пакета устройства.

ВОПРОС BB-10. Как рецепт задаёт исходники и патчи?

Ответ: SRC_URI перечисляет источники, патчи и дополнительные файлы. Для архивов проверяются контрольные суммы. Для Git фиксируется нужная ревизия. Настройки ветки и каталога исходников должны соответствовать выбранной версии.

Пример и проверка: Для локального патча SDK он должен быть указан в SRC_URI и найден через настроенные пути поиска. Выбранная ревизия исходников должна позволять применить патч. Проверяйте эти три условия вместе. Файл в слое ещё не доказывает его получение и применение.

ВОПРОС BB-11. Почему .bbappend может не примениться?

Ответ: Его имя не совпадает с выбранным рецептом, слой не подключён или используется другой рецепт. Проверьте show-layers, show-appends и итоговые настройки. Изменение неприменённого .bbappend не влияет на сборку.

Пример и проверка: После изменения append проверьте show-appends и итоговые значения рецепта. Учитывайте синтаксис релиза проекта. Различайте переопределения пакетов и обычные суффиксы переменных. Это надёжнее предположения о совпадении имени или автоматической замены всех подчёркиваний.

ВОПРОС BB-12. Зачем нужен FILESEXTRAPATHS?

Ответ: Он добавляет каталоги поиска локальных файлов рецепта, например патчей из своего слоя. Указать file:// в SRC_URI недостаточно: BitBake должен ещё найти файл. Настройку поиска ограничивают нужным рецептом.

Пример и проверка: Для локального патча SDK он должен быть указан в SRC_URI и найден через настроенные пути поиска. Выбранная ревизия исходников должна позволять применить патч. Проверяйте эти три условия вместе. Файл в слое ещё не доказывает его получение и применение.

ВОПРОС BB-13. Зачем наследовать класс системы сборки?

Ответ: Классы cmake и autotools уже описывают типовые шаги и настройку кросс-компиляции. Рецепту остаётся задать зависимости и параметры проекта. Самодельные команды могут случайно использовать компилятор или библиотеки сборочного компьютера.

Пример и проверка: Для CMake-компонента SDK начните с класса cmake и проверьте сформированную команду настройки. Добавляйте настройки проекта и недостающие зависимости. У вложенных сборок проверьте тот же toolchain. Переписывание стандартных шагов может незаметно потерять поддержку кросс-компиляции.

ВОПРОС BB-14. Как связаны кросс-компиляция и sysroot?

Ответ: Компилятор создаёт код для устройства. Sysroot рецепта содержит нужные заголовки и библиотеки устройства из объявленных зависимостей. Генераторы, запускаемые при сборке на компьютере, требуют native-вариантов. Наличие программы в PATH не доказывает нужную архитектуру.

Пример и проверка: Например, при сборке приложению нужны заголовки SDK, а телефону — пакеты рабочих библиотек. Генератор исходников запускается на сборочном компьютере. Для каждого компонента определите сторону использования. Это предотвращает отсутствие пакетов на телефоне и случайные библиотеки компьютера.

ВОПРОС BB-15. Что задаёт PACKAGECONFIG?

Ответ: Он выбирает дополнительные возможности рецепта и может связывать их с параметрами настройки и зависимостями. Проверьте итоговое значение и поддержку выбранной возможности в исходниках. Отключение одного флага ещё не доказывает уменьшение размера или памяти.

Пример и проверка: Удаление ненужной функции может убрать её код и зависимости, но удаление нужного codec сломает звонки. Сравните одинаковую нагрузку на устройстве до и после. Symbols для диагностики храните отдельно от рабочего образа. Сообщайте только реально измеренное изменение размера или памяти.

ВОПРОС BB-16. Как связаны PACKAGES и FILES?

Ответ: PACKAGES перечисляет выходные пакеты. FILES определяет, какие установленные файлы входят в каждый из них. Один рецепт может создать обычный пакет, пакет для разработки и пакет отладки. Если файл потерялся, проверьте это распределение.

Пример и проверка: Возьмите один пропавший файл и проследите его из ${D} в пакет и затем в образ. Так находится этап потери. Заголовок может правильно относиться к -dev, а не рабочему пакету. Исправляйте распределение, а не помещайте все файлы в один пакет.

ВОПРОС BB-17. Что означает installed-vs-shipped?

Ответ: Рецепт установил файл, но не включил его ни в один пакет. Исправьте путь установки или правило FILES; ненужный файл не устанавливайте. Глобальное отключение проверки может скрыть отсутствие нужных файлов на устройстве.

Пример и проверка: Возьмите один пропавший файл и проследите его из ${D} в пакет и затем в образ. Так находится этап потери. Заголовок может правильно относиться к -dev, а не рабочему пакету. Исправляйте распределение, а не помещайте все файлы в один пакет.

ВОПРОС BB-18. Как работают сигнатуры задач и sstate?

Ответ: Сигнатура описывает входные данные и настройки задачи. При совпадении можно взять готовый результат из sstate. Если зависимость не объявлена, изменение может остаться незамеченным. Поэтому проверяют зависимости и сигнатуры, а не сразу обвиняют кеш.

Пример и проверка: Например, необъявленный вход может не изменить сигнатуру задачи. Очистка даст одну удачную сборку, но описание останется неверным. Найдите и объявите пропущенный вход. Затем проверьте нужную пересборку при его изменении без постоянного удаления всего кеша.

ВОПРОС BB-19. Чем отличаются clean, cleansstate и cleanall?

Ответ: clean удаляет рабочие результаты рецепта, но оставляет sstate. cleansstate удаляет также локальный sstate; удалённые зеркала учитываются отдельно. cleanall дополнительно удаляет загруженные исходники. Осторожно применяйте их при общих каталогах загрузок и кеша.

Пример и проверка: Например, необъявленный вход может не изменить сигнатуру задачи. Очистка даст одну удачную сборку, но описание останется неверным. Найдите и объявите пропущенный вход. Затем проверьте нужную пересборку при его изменении без постоянного удаления всего кеша.

ВОПРОС BB-20. Как проверить неверный выбор рецепта или зависимости?

Ответ: Посмотрите итоговые настройки, правила выбора версии и граф зависимостей, например через bitbake -g. Различайте зависимости рецептов при сборке и зависимости пакетов на устройстве. Исправляйте описание зависимости, а не случайный порядок запуска задач.

Пример и проверка: Если опция SDK не действует, найдите итоговое значение и посмотрите, какой рецепт, append или настройка его изменили. Проверьте выбранный рецепт и версию. Иначе изменение другой копии файла может выглядеть как ошибка системы сборки.

ВОПРОС BB-21. Нужно ли в Honister заменять все подчёркивания двоеточиями?

Ответ: Нет. Изменился синтаксис переопределений, например :append и FILES:${PN}. Обычные имена переменных и некоторые суффиксы остались прежними. Каждую замену нужно проверять по смыслу.

Пример и проверка: После изменения append проверьте show-appends и итоговые значения рецепта. Учитывайте синтаксис релиза проекта. Различайте переопределения пакетов и обычные суффиксы переменных. Это надёжнее предположения о совпадении имени или автоматической замены всех подчёркиваний.

ВОПРОС BB-22. Зачем отдельные пакеты -dev и -dbg?

Ответ: -dev обычно содержит заголовки и файлы для подключения библиотеки при сборке. -dbg содержит отладочные данные. Для запуска обычно нужны программа и рабочие библиотеки. Точный состав определяется правилами и порядком разбиения пакетов.

Пример и проверка: Телефону обычно не нужны заголовки для запуска готовой программы. SDK разработчика нужны они для компиляции. Отладочные файлы имеют третью задачу — связать стек со сборкой. Перед добавлением файлов разработки в рабочий образ определите их потребителя.

ВОПРОС BB-23. Как devtool modify и finish сохраняют изменения?

Ответ: modify подготавливает исходники существующего рецепта для редактирования. После commit команда finish переносит изменения и патчи в выбранный слой и снимает временное переопределение из workspace. Затем нужно проверить сборку уже из этого слоя.

Пример и проверка: Workspace может давать рабочий результат, хотя в основном слое патча нет. Экспортируйте зафиксированные изменения и проверьте рецепт или append. Затем соберите без временной подмены workspace. Это проверяет то, что реально получит другой разработчик или CI.

ВОПРОС BB-24. Добавляет ли inherit pkgconfig отсутствующую библиотеку?

Ответ: Нет. Он настраивает pkg-config для кросс-компиляции. Рецепт библиотеки всё равно нужно указать в DEPENDS, чтобы её заголовки, библиотеки и .pc-файлы появились в sysroot.

Пример и проверка: Например, при сборке приложению нужны заголовки SDK, а телефону — пакеты рабочих библиотек. Генератор исходников запускается на сборочном компьютере. Для каждого компонента определите сторону использования. Это предотвращает отсутствие пакетов на телефоне и случайные библиотеки компьютера.

ВОПРОС BB-25. Гарантируют ли -Os и удаление symbols меньший расход RAM?

Ответ: Нет. Размер кода, отладочные данные и память под рабочие буферы — разные вещи. Сравнивайте одинаковую нагрузку на устройстве и храните symbols отдельно. Проверяйте возможности именно установленной версии GCC.

Пример и проверка: Удаление ненужной функции может убрать её код и зависимости, но удаление нужного codec сломает звонки. Сравните одинаковую нагрузку на устройстве до и после. Symbols для диагностики храните отдельно от рабочего образа. Сообщайте только реально измеренное изменение размера или памяти.

ВОПРОС BB-26. Почему SDK есть в пакетах, но приложение не запускается?

Ответ: Может не совпадать SONAME или ABI библиотеки, отсутствовать подключаемый модуль либо данные. Проверьте файлы, зависимости ELF и пути поиска. Для анализа не пытайтесь запускать ARM-программу на сборочном компьютере.

Пример и проверка: Если телефон не загружает Linphone, сравните требования программы с библиотеками образа. Проверьте имена, совместимость и пути plugins и данных. Библиотека в каталоге сборки не равна установленной на телефоне. До пересборки подтвердите фактический релиз устройства.
