BSP

РАЗДЕЛ 1. ТЕХНОЛОГИЯ И ВЕРСИЯ

Категория: Встроенная платформа

Board support package для конкретной платы NXP i.MX и релиза производителя.

РАЗДЕЛ 2. НАЗНАЧЕНИЕ

BSP, или board support package, — это программы и настройки для запуска системы на конкретной плате. Он связывает операционную систему с оборудованием платы.

РАЗДЕЛ 3. ОСНОВНЫЕ ПОНЯТИЯ

- В BSP обычно входят поддержка загрузчика и ядра, настройки платы, описание устройств, драйверы и нужные firmware. Точный состав зависит от производителя и продукта.
- Корневая файловая система содержит программы и данные пользовательской части. Она работает вместе с BSP, но не является тем же самым.
- Device tree описывает подключения и ресурсы оборудования. Драйверы всё равно должны поддерживать эти устройства.
- Параметры ядра, модули и firmware определяют возможность запуска устройств. Затем на доступ приложения влияют файлы устройств и права.
- Производитель и продуктовые слои могут делить эти задачи. Перед названием «изменение BSP» проверьте, что именно менялось.
- Запуск новой платы, сопровождение платформы и интеграция приложения — разные уровни работы. Личный вклад нужно описывать точно.
- Ядро, загрузчик, device tree и rootfs должны иметь совместимые версии и проверенный путь восстановления.

РАЗДЕЛ 4. ТИПИЧНОЕ ИСПОЛЬЗОВАНИЕ

Начните с ревизии платы, релиза BSP и конфигурации machine. Проследите логи загрузчика и ядра, проверьте device tree и драйвер, затем наличие firmware и user-space пакетов. Проверяйте на физическом оборудовании и фиксируйте использованную конфигурацию.

Для предполагаемого изменения BSP сначала сопоставьте реальную ревизию платы и поддерживаемый релиз производителя. Проследите затронутый путь от загрузочных артефактов через device tree и драйвер до приложения user space.

Зафиксируйте исходную конфигурацию, соберите и разверните соответствующие артефакты в подходящем тестовом окружении, затем проверьте загрузку, периферию и документированный способ восстановления. Если устройство есть в Linux, но не открывается, причиной могут быть права или конфигурация user space, а не отсутствие драйвера BSP.

WORKFLOW ЯДРА, МОДУЛЕЙ И DEVICE TREE

BSP может включать ветки ядра и U-Boot производителя, настройки платы, firmware и нужные компоненты GPU/VPU/NPU. Закрытые компоненты требуются не каждой плате. Примеры слоёв — meta-raspberrypi, meta-freescale с NXP meta-imx и meta-ti. Их ветки и зависимости согласуются с релизом Yocto.

KERNEL-01. Изменить provider.

- Определить provider virtual/kernel.
- Выполнить devtool modify virtual/kernel, где поддерживается, либо использовать разрешённое имя рецепта; в упражнении QEMU это linux-yocto.
- Изменить workspace sources, сделать отдельный Git commit, собрать и проверить.
- Либо экспортировать через devtool finish linux-yocto ../meta-lab, либо вручную использовать git format-patch -1 в репозитории исходников.

В ручном варианте положить патч в files/ рядом с linux-yocto_%.bbappend собственного слоя, содержащим:

```bitbake
FILESEXTRAPATHS:prepend := "${THISDIR}/files:"
SRC_URI += "file://0001-lab-change.patch"
```

- Имя файла совпадает с экспортированным патчем.
- При ручном экспорте после сохранения патча снять workspace override через devtool reset linux-yocto; finish уже снимает его.
- Затем проверить сборку из слоя.
- Нельзя применять один патч дважды через оба способа экспорта.

Подготовка исходников в workspace для примера QEMU:

```bash
devtool modify linux-yocto
```

После редактирования, commit и проверки — экспорт через devtool:

```bash
devtool finish linux-yocto ../meta-lab
```

Альтернатива — ручной экспорт из Git-каталога исходников:

```bash
git format-patch -1
```

После сохранения патча и добавления append при ручном экспорте:

```bash
devtool reset linux-yocto
```

KERNEL-02. Сохранить конфигурацию.

- Выполнить bitbake -c menuconfig virtual/kernel, сохранить, затем bitbake -c diffconfig virtual/kernel, если provider поддерживает задачи.
- Скопировать фрагмент из указанного командой места в files/lab.cfg и добавить SRC_URI += "file://lab.cfg" в append.
- Для упражнения linux-yocto фрагмент может содержать CONFIG_PRINTK_TIME=y.
- Проверить итоговую .config и поведение после загрузки.
- Если vendor-рецепт не объединяет fragments, нужен поддерживаемый им механизм конфигурации; одной загрузки .cfg недостаточно.

```bash
bitbake -c menuconfig virtual/kernel
bitbake -c diffconfig virtual/kernel
```

linux-yocto_%.bbappend:

```bitbake
SRC_URI += "file://lab.cfg"
```

files/lab.cfg:

```ini
CONFIG_PRINTK_TIME=y
```

KERNEL-03. Упаковать внешний модуль.

- Использовать inherit module и Makefile, совместимый с интерфейсом сборки ядра.
- Рецепт собирается против выбранного ядра и упаковывает установленные .ko.
- KERNEL_MODULE_AUTOLOAD += "lab_driver" запрашивает загрузку при старте, но не выбирает пакет модуля в образ.
- Включить реальный выходной пакет, проверить modinfo/modprobe и dmesg, пересобирать при изменениях ABI/configuration ядра.

Фрагмент рецепта внешнего модуля:

```bitbake
inherit module
KERNEL_MODULE_AUTOLOAD += "lab_driver"
```

DT-01. Собрать и выбрать описание.

- .dts описывает плату; .dtsi хранит общие описания.
- Preprocessing в kernel build и dtc создают .dtb.
- compatible участвует в сопоставлении с драйвером, но также нужны сам драйвер, clocks, regulators, pinctrl и firmware.
- KERNEL_DEVICETREE в machine configuration выбирает outputs у поддерживающих её рецептов.
- Добавление нового .dts через append к ядру обычно требует патча соответствующего build Makefile и выбора output; один fetch не обеспечивает сборку/поставку.

DT-02. Применить overlay.

- Overlay использует /plugin/ и компилируется в .dtbo.
- Overlay, который ссылается на символы базового дерева, требует соответствующих сведений о символах. Обычно базовое дерево и overlay собирают с dtc -@.
- U-Boot загружает их, выбирает FDT, выделяет место через fdt resize и применяет overlay через fdt apply перед запуском Linux.
- Адреса/команды загрузки зависят от платы.
- Firmware Raspberry Pi вместо этого использует dtoverlay= в config.txt.
- После загрузки проверяются живое дерево и probe драйвера; поставленный .dtbo не доказывает применение.

ВОССТАНОВЛЕНИЕ КОМПОНЕНТОВ И ВОССТАНОВЛЕНИЕ ПЛАТЫ

- Сервис внутри Linux может вернуть прежнее приложение, пока базовая система загружается. Он не обязан исправлять сломанный загрузчик, нечитаемый корневой раздел или несовместимый device tree. Для этого нужен отдельный способ восстановления платы.
- Serial UART console помогает наблюдать boot и выполнять поддерживаемые команды загрузчика, но не доказывает передачу самой прошивки через UART. Перед описанием подтверждается реальный транспорт перепрошивки платы.
- Переключение каталогов версий приложения не равно A/B-обновлению ядра и rootfs. Для второго отдельно настраиваются загрузчик, счётчик попыток и подтверждение успешного запуска.

РАЗДЕЛ 5. ПРЕИМУЩЕСТВА, ОГРАНИЧЕНИЯ И АЛЬТЕРНАТИВЫ

BSP производителя ускоряет поддержку оборудования и даёт проверенную основу для поддерживаемых конфигураций. Одновременно возникают зависимости от релизов, патчей и совместимых слоёв производителя. Mainline может упростить сопровождение при достаточной поддержке оборудования и функций; компромисс оценивается для конкретного устройства.

РАЗДЕЛ 6. ОШИБКИ И БЕЗОПАСНОСТЬ

Корректное приложение не исправит несовпадающий device tree, отсутствующий драйвер или неверный загрузочный артефакт. Обновление BSP может изменить интерфейсы ядра или требования к firmware; проверяйте периферию, загрузку и обновление вместе. Сохраняйте способы восстановления и проверяйте подлинность артефактов обновления, когда это применимо.

РАЗДЕЛ 7. ИСПОЛЬЗОВАНИЕ В ПРОЕКТАХ КАНДИДАТА

До прихода нашей команды существовала базовая заготовка платформы Yocto. Linphone SDK, WebRTC и mediasoup в ней отсутствовали. Наша команда добавила эти компоненты и интегрировала их сборочные зависимости, пакеты и требования при работе на устройстве в образ телефона. Мой личный вклад включал приложение/SDK, метаданные BitBake, упаковку, интеграцию образа и проверку на устройстве; интеграция всего стека была командной работой.

РАЗДЕЛ 8. ВОПРОСЫ НА ИНТЕРВЬЮ

ВОПРОС BSP-01. Что такое BSP?

Ответ: Это набор программ и настроек для работы ОС на конкретной плате. Обычно он включает загрузочные компоненты, ядро, описание оборудования, драйверы и firmware. Его состав зависит от производителя и продукта.

Пример и проверка: Телефону нужны и рабочая поддержка оборудования, и библиотеки с настройками приложения. Они могут поставляться вместе, но относятся к разной работе. Определите вклад производителя и продуктовых слоёв. Тогда проще найти ответственного за отказ и совместимость обновления.

ВОПРОС BSP-02. BSP и корневая файловая система — одно и то же?

Ответ: Нет. Корневая файловая система содержит программы и данные пользовательской части. BSP обеспечивает поддержку оборудования. В готовом устройстве эти части должны быть согласованы, даже если собираются в одном процессе.

Пример и проверка: Телефону нужны и рабочая поддержка оборудования, и библиотеки с настройками приложения. Они могут поставляться вместе, но относятся к разной работе. Определите вклад производителя и продуктовых слоёв. Тогда проще найти ответственного за отказ и совместимость обновления.

ВОПРОС BSP-03. Зачем нужен device tree?

Ответ: Он описывает подключения оборудования и необходимые ресурсы. Драйвер читает подходящее описание по правилам bindings. Device tree не заменит отсутствующий драйвер и не исправит ошибку разводки платы.

Пример и проверка: Например, включение узла камеры не создаёт отсутствующий код драйвера. Сначала проверьте binding, ресурсы и поддерживаемый compatible. Адреса, clocks и GPIO должны соответствовать плате. Затем смотрите сообщения запуска драйвера, до проверки полного приложения.

ВОПРОС BSP-04. Что может нарушить обновление BSP?

Ответ: Могут измениться совместимость загрузчика, ядра и DTB, драйверы, firmware и интерфейсы приложений. Проверяйте загрузку, периферию и восстановление. Успешный старт ядра ещё не доказывает работу камеры и звука.

Пример и проверка: После изменения платформы повторите важные аппаратные сценарии приложения, даже если компиляция проходит. Могли измениться пути устройств, права, время готовности и поддержка медиа. Зафиксируйте образ и плату. Полезный результат указывает работающие функции на этой комбинации.

ВОПРОС BSP-05. Означает ли использование BSP ответственность за весь BSP?

Ответ: Нет. Интеграция приложения с готовым BSP отличается от создания и сопровождения всех его частей. Называйте конкретные свои изменения и проверки, не приписывая себе всю работу с платой.

Пример и проверка: Например, адаптация пакета или сервиса к готовому BSP не равна самостоятельному запуску платы. Назовите точный файл или интерфейс изменения. Затем покажите проверку на устройстве. Это сильнее как заявления обо всём BSP, так и обесценивания интеграции.

ВОПРОС BSP-06. Достаточно ли наличия файла устройства для работы приложения?

Ответ: Нет. Нужны правильный драйвер, успешная инициализация оборудования, права и настройки приложения. Файл в /dev не доказывает, что камера уже передаёт кадры или аудиоустройство правильно настроено.

Пример и проверка: Начните с минимальной проверки устройства до полного UI. Если драйвер не запускается, изменение звонков Qt вряд ли поможет. Если устройство работает, но сервис не имеет доступа, проверьте права и окружение. Ищите первую отказавшую часть, а не только показавший ошибку слой.

ВОПРОС BSP-07. Как проверить обновление BSP?

Ответ: Зафиксируйте исходные версии и сравните загрузку, устройства, приложение и настройки после обновления. Проверьте обычные и аварийные сценарии, включая восстановление. Используйте реальную плату и сохраните способ возврата к рабочей системе.

Пример и проверка: После изменения платформы повторите важные аппаратные сценарии приложения, даже если компиляция проходит. Могли измениться пути устройств, права, время готовности и поддержка медиа. Зафиксируйте образ и плату. Полезный результат указывает работающие функции на этой комбинации.

ВОПРОС BSP-08. Какие части загрузки должны быть совместимы?

Ответ: Загрузчик, ядро, DTB, возможный initramfs, разметка и корневая файловая система. Проверяйте, какие файлы реально загружаются. Совпадения имён или наличия свежего ядра недостаточно.

Пример и проверка: Новое ядро со старым несовместимым DTB может отказать, хотя оба файла есть. Проверьте фактический выбор загрузчика и разметку. Учитывайте rootfs и раннюю пользовательскую часть. Сохраняйте рабочую комбинацию на время проверки новой.

ВОПРОС BSP-09. Когда достаточно исправить device tree, а когда нужен драйвер?

Ответ: Если драйвер поддерживает устройство, но неверно описаны ресурсы, может хватить device tree. Если нужного поведения в драйвере нет, одной правкой описания его не добавить. Проверьте bindings и сообщения инициализации.

Пример и проверка: Например, включение узла камеры не создаёт отсутствующий код драйвера. Сначала проверьте binding, ресурсы и поддерживаемый compatible. Адреса, clocks и GPIO должны соответствовать плате. Затем смотрите сообщения запуска драйвера, до проверки полного приложения.

ВОПРОС BSP-10. Зачем нужны defconfig и фрагменты конфигурации?

Ответ: Они сохраняют выбор возможностей ядра в метаданных сборки. Проверьте итоговую .config: зависимости могут изменить запрошенное значение. Для vendor-ядра нужно учитывать поддерживаемый им способ настройки.

Пример и проверка: Для опции ядра смотрите итоговую .config после обработки фрагментов и зависимостей. Значение может быть заменено или зависеть от другой опции. Подтвердите поддержку fragments vendor-рецептом. Затем проверьте нужное поведение работающего ядра.

ВОПРОС BSP-11. Чем отличаются встроенный драйвер, модуль и firmware?

Ответ: Встроенный драйвер входит в ядро. Модуль загружается отдельно. Firmware — данные или программа, которые могут требоваться самому устройству. Все нужные части должны попасть в поставку и соответствовать версии системы.

Пример и проверка: Модуль должен быть собран для выбранного ядра и включён в образ. Нужная firmware тоже устанавливается. Autoload лишь запрашивает загрузку и не предоставляет эти файлы. На телефоне проверьте загрузку модуля и сообщения ядра.

ВОПРОС BSP-12. Зачем последовательная консоль при запуске платы?

Ответ: Она позволяет видеть ранние сообщения загрузки, когда графика и сеть ещё не работают. Это помогает найти отказавший этап и использовать поддерживаемый путь восстановления. Наличие консоли не определяет способ передачи прошивки.

Пример и проверка: Последовательная консоль может показывать prompt загрузчика, хотя данные прошивки передаются другим интерфейсом. Запишите команды управления и реальный путь данных. Не называйте процесс UART-перепрошивкой только по serial output. Используйте процедуру конкретной платы.

ВОПРОС BSP-13. Зачем читать bindings вместо копирования узлов?

Ответ: Bindings описывают допустимые свойства и ресурсы устройства. Узел с другой платы может иметь неверные адреса, питание и GPIO. Сверяйте описание с драйвером и схемой своей платы.

Пример и проверка: Например, включение узла камеры не создаёт отсутствующий код драйвера. Сначала проверьте binding, ресурсы и поддерживаемый compatible. Адреса, clocks и GPIO должны соответствовать плате. Затем смотрите сообщения запуска драйвера, до проверки полного приложения.

ВОПРОС BSP-14. Как понять, какой DTB действительно загружен?

Ответ: Проверьте настройку загрузчика, его вывод и описание оборудования работающей системы. Сопоставьте с ожидаемой сборкой. Новый файл в каталоге сборки не означает, что загрузчик выбрал его.

Пример и проверка: Сравните дерево работающей системы с ожидаемыми изменениями платы. Для overlay подтвердите применение при загрузке, а не только копирование в результаты сборки. Затем проверьте подключение драйвера и поведение. Правка исходника без изменения рабочего дерева устройство не исправит.

ВОПРОС BSP-15. В каком порядке запускать новую плату?

Ответ: Сначала проверьте питание, консоль и загрузочный путь. Затем память, ядро, корневую файловую систему и базовые интерфейсы. После этого добавляйте периферию и приложение, проверяя каждый этап отдельно.

Пример и проверка: Запускайте этапы по одному и добивайтесь повторяемости до следующего. Начните с наблюдения и доступа для восстановления, затем накопителя и базовой системы. После добавляйте периферию и приложение. Так при новом отказе меньше возможных причин.

ВОПРОС BSP-16. Что нельзя забыть при изменении BSP?

Ответ: Приложения могут зависеть от имён устройств, прав, форматов данных, ABI и времени готовности сервисов. Проверьте эти ожидания после изменения платформы. Сохранение компиляции не гарантирует сохранение поведения.

Пример и проверка: После изменения платформы повторите важные аппаратные сценарии приложения, даже если компиляция проходит. Могли измениться пути устройств, права, время готовности и поддержка медиа. Зафиксируйте образ и плату. Полезный результат указывает работающие функции на этой комбинации.

ВОПРОС BSP-17. Как отличить ошибку приложения от проблемы платформы?

Ответ: Найдите первую неработающую границу: обнаружение оборудования, драйвер, права, сервис или логика приложения. Сравните логи и минимальный сценарий на устройстве. Не меняйте UI только потому, что ошибка видна на экране.

Пример и проверка: Начните с минимальной проверки устройства до полного UI. Если драйвер не запускается, изменение звонков Qt вряд ли поможет. Если устройство работает, но сервис не имеет доступа, проверьте права и окружение. Ищите первую отказавшую часть, а не только показавший ошибку слой.

ВОПРОС BSP-18. Что нужно передать разработчикам приложения вместе с BSP?

Ответ: Поддерживаемые платы и версии, состав образа, настройки устройств, известные ограничения и инструкции проверки и восстановления. Это даёт воспроизводимую основу вместо неизвестного набора файлов.

Пример и проверка: Хорошая передача позволяет другому инженеру воспроизвести образ и проверить базовую функцию устройства. Нужны версии, включённые возможности и ограничения. Опишите сбор сведений запуска и восстановление платы. Один каталог бинарников такого рабочего соглашения не даёт.

ВОПРОС BSP-19. Что проверить при обновлении и recovery?

Ответ: Подлинность и совместимость пакета, сохранность данных, отключение питания и возврат к рабочему состоянию. После обновления и отката проверьте холодный запуск, периферию и приложение. Старый образ бесполезен, если новая схема данных не даёт им пользоваться.

Пример и проверка: Откат приложения предполагает работающие Linux и updater. Если загрузчик или rootfs не работают, каталога старого приложения недостаточно. Проверьте отдельный случай процедурой восстановления платы. Не смешивайте его с успешным возвратом файлов телефонного приложения.

ВОПРОС BSP-20. Чем настройка BSP отличается от его использования?

Ответ: Использование опирается на готовые интерфейсы платы. Настройка означает конкретные изменения machine, загрузчика, ядра, DTB, драйвера или firmware и проверку результата. Небольшая правка не равна созданию всей платформы.

Пример и проверка: Например, адаптация пакета или сервиса к готовому BSP не равна самостоятельному запуску платы. Назовите точный файл или интерфейс изменения. Затем покажите проверку на устройстве. Это сильнее как заявления обо всём BSP, так и обесценивания интеграции.

ВОПРОС BSP-21. Любой ли рецепт ядра применит .cfg из SRC_URI?

Ответ: Нет. Рецепт должен поддерживать объединение фрагментов. Проверьте итоговую .config и зависимости параметров. Vendor-рецепт может требовать другой способ настройки.

Пример и проверка: Для опции ядра смотрите итоговую .config после обработки фрагментов и зависимостей. Значение может быть заменено или зависеть от другой опции. Подтвердите поддержку fragments vendor-рецептом. Затем проверьте нужное поведение работающего ядра.

ВОПРОС BSP-22. Добавляет ли KERNEL_MODULE_AUTOLOAD модуль в образ?

Ответ: Нет. Он настраивает загрузку модуля при старте. Пакет самого модуля нужно включить отдельно. Проверьте соответствие ядру и успешный modprobe на устройстве.

Пример и проверка: Модуль должен быть собран для выбранного ядра и включён в образ. Нужная firmware тоже устанавливается. Autoload лишь запрашивает загрузку и не предоставляет эти файлы. На телефоне проверьте загрузку модуля и сообщения ядра.

ВОПРОС BSP-23. Почему узел с compatible может не работать?

Ответ: Узел может быть выключен, драйвер отсутствовать или его инициализация откладываться из-за питания, clocks, pinctrl или firmware. Проверяйте описание работающей системы и сообщения ядра.

Пример и проверка: Сравните дерево работающей системы с ожидаемыми изменениями платы. Для overlay подтвердите применение при загрузке, а не только копирование в результаты сборки. Затем проверьте подключение драйвера и поведение. Правка исходника без изменения рабочего дерева устройство не исправит.

ВОПРОС BSP-24. Как подтвердить применение overlay?

Ответ: Нужные узлы и свойства должны появиться в работающем device tree, а драйвер — успешно подключиться к устройству. Один собранный или скопированный .dtbo не доказывает его применение загрузчиком.

Пример и проверка: Сравните дерево работающей системы с ожидаемыми изменениями платы. Для overlay подтвердите применение при загрузке, а не только копирование в результаты сборки. Затем проверьте подключение драйвера и поведение. Правка исходника без изменения рабочего дерева устройство не исправит.

ВОПРОС BSP-25. Восстановит ли откат приложения незагружающуюся плату?

Ответ: Нет. Такой updater требует работающего Linux. Для отказа загрузчика или rootfs нужен отдельный поддерживаемый путь восстановления платы. Сохранённый старый executable Qt этого не обеспечивает.

Пример и проверка: Откат приложения предполагает работающие Linux и updater. Если загрузчик или rootfs не работают, каталога старого приложения недостаточно. Проверьте отдельный случай процедурой восстановления платы. Не смешивайте его с успешным возвратом файлов телефонного приложения.

ВОПРОС BSP-26. Доказывает ли UART-консоль перепрошивку через UART?

Ответ: Нет. Через консоль можно управлять загрузчиком, который получает образ по другому интерфейсу. Различайте управление, просмотр сообщений и передачу самого образа. Для утверждения нужен точный порядок перепрошивки платы.

Пример и проверка: Последовательная консоль может показывать prompt загрузчика, хотя данные прошивки передаются другим интерфейсом. Запишите команды управления и реальный путь данных. Не называйте процесс UART-перепрошивкой только по serial output. Используйте процедуру конкретной платы.

ВОПРОС BSP-27. Что такое DTB и нужен ли отдельный рецепт для его сборки?

Ответ: DTB означает Device Tree Blob — скомпилированное двоичное описание оборудования платы. Исходник обычно состоит из файла .dts и подключаемых файлов .dtsi. В нём описываются память, шины, GPIO-контроллеры, настройка выводов и подключённые устройства. На типичной ARM-системе с device tree загрузчик передаёт это описание ядру. DTB содержит данные, а не код драйверов; это не ядро и не корневая файловая система.

Пример и проверка: Обычный путь: .dts с подключаемыми описаниями, предварительная обработка при сборке ядра и dtc, затем .dtb в загрузочных файлах. Отдельный рецепт для каждого DTB обычно не нужен: выбранные деревья собирает существующий рецепт ядра/BSP, часто по KERNEL_DEVICETREE. Изменения платы обычно оформляются дополнением или патчем к этому поставщику в слое продукта. Возможна и отдельная сборка device tree — это зависит от BSP. В конце проверяется, какое дерево реально загружает загрузчик: DTB, оставшийся в каталоге сборки, поведение телефона не изменит.
