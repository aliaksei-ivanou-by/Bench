Yocto-Project

РАЗДЕЛ 1. ТЕХНОЛОГИЯ И ВЕРСИЯ

Категория: Система сборки

Yocto Project 4.0 Kirkstone. Точная версия определяется настройками сборки проекта.

РАЗДЕЛ 2. НАЗНАЧЕНИЕ

Yocto Project помогает собрать Linux для конкретного устройства. Вы выбираете программы, библиотеки и настройки образа. OpenEmbedded предоставляет рецепты и настройки сборки, а BitBake читает их и выполняет задачи.

РАЗДЕЛ 3. ОСНОВНЫЕ ПОНЯТИЯ

- Рецепт описывает, откуда получить компонент и как его собрать, установить и упаковать.
- Класс содержит общие шаги для нескольких рецептов. Слой объединяет рецепты и настройки. .bbappend дополняет подходящий рецепт.
- MACHINE выбирает настройки платы. DISTRO задаёт общие правила системы. Образ выбирает устанавливаемые пакеты.
- Sysroot рецепта — каталог заголовков и библиотек устройства, нужных для сборки этого рецепта. SDK даёт компилятор и библиотеки для разработки вне полной сборки образа.
- Один рецепт может создать несколько пакетов. Успешная сборка не означает, что эти пакеты включены в образ.
- Sstate хранит готовые результаты задач. Он ускоряет сборку, но не проверяет телефон.
- Результаты сборки хранятся отдельно от исходных слоёв. Если несколько слоёв влияют на компонент, проверяются выбранный рецепт и итоговые настройки.
- Созданный SDK должен соответствовать устройству. Кроме локальных тестов логики нужна проверка итогового образа на оборудовании.

РАЗДЕЛ 4. ТИПИЧНОЕ ИСПОЛЬЗОВАНИЕ

После подключения среды сборки проекта bitbake <image> собирает образ; bitbake-layers show-layers показывает включённые слои, а bitbake-layers show-appends — применённые расширения. Проверяют local.conf и bblayers.conf, логи сборки, состав пакетов и итоговую корневую файловую систему. Используют документацию релиза и конфигурацию machine проекта; результат команд зависит от подключённых слоёв.

Практическая проверка: сначала определите MACHINE, DISTRO и версии подключённых слоёв. Если файла нет на устройстве, проверьте установку рецепта, наличие файла в собранном пакете, выбор пакета в образ и развёртывание именно нужного образа.

oe-pkgdata-util исследует данные уже собранных пакетов: find-path находит пакет по пути, list-pkg-files показывает файлы пакета. После проверки образа проверьте права и конфигурацию сервиса на устройстве.

FLOW ИНТЕГРАЦИИ LINPHONE SDK

Это общий пример интеграции. Здесь linphone-sdk — имя рецепта SDK, phone-ui — рецепт использующего его приложения, phone-image — рецепт продуктового образа. Реальные имена рецептов и выходных пакетов зависят от настроек сборки. Linphone SDK — библиотеки телефонии. Yocto SDK — компилятор и библиотеки для разработки под устройство. Это разные наборы ПО.

FLOW-01. Выбрать исходную сборку.

- Начните с работающего образа платы.
- Запишите MACHINE, DISTRO, версии слоёв, компилятор и C library. Слои должны поддерживать Kirkstone.
- Выберите релиз SDK, совместимый с этой сборкой и API приложения.
- Определите, нужны ли звук, видео, TLS и какие кодеки. Самый новый upstream-код не обязательно подходит старой ветке продукта.

FLOW-02. Найти готовый рецепт.

- В Linux-окружении сборки посмотрите подключённые слои, рецепты и appends.
- Найдите liblinphone и связанные компоненты. Рецепт может называться иначе.
- По возможности используйте совместимый рецепт и .bbappend своего слоя. Новый рецепт нужен, если готовые не собирают нужную версию.

```bash
bitbake-layers show-layers
bitbake-layers show-recipes
bitbake-layers show-appends
```

FLOW-03. Разместить изменения в продуктовом слое.

- Используйте готовый продуктовый слой либо создайте и подключите meta-phone.
- Проверьте conf/layer.conf: какие рецепты он находит, какие слои требует и поддерживает ли Kirkstone.
- Возможный каталог — meta-phone/recipes-connectivity/linphone-sdk/, патчи находятся в files/.
- Постоянное исправление не должно оставаться только в чужом слое или временном каталоге сборки.

```bash
bitbake-layers create-layer ../meta-phone
bitbake-layers add-layer ../meta-phone
```

FLOW-04. Зафиксировать исходники и проверить лицензии.

- Задайте SUMMARY, LICENSE, LIC_FILES_CHKSUM, SRC_URI, SRCREV и S для выбранных исходников.
- Зафиксируйте Git commit и получайте все исходники через BitBake. Проверьте суммы release-архивов и нужные submodules.
- Храните изменения как патчи в SRC_URI либо фиксированный commit сопровождаемого fork.
- Проверьте лицензии SDK, включённых codecs и остальных зависимостей.

FLOW-05. Выбрать способ сборки зависимостей.

- Linphone SDK может сам собирать несколько компонентов через CMake. Изучите настройки выбранного релиза.
- Где поддерживается, собирайте зависимости отдельными рецептами Yocto. Иначе адаптируйте сборку SDK так, чтобы Yocto контролировал исходники, compiler и установку.
- Исключите загрузки во время configure/compile и конфликтующие встроенную и системную копии библиотеки.
- Не предполагайте один и тот же переключатель отключения общей сборки, или superbuild, во всех версиях SDK.

FLOW-06. Настроить сборку под устройство.

- Для CMake-компонента используйте inherit cmake и укажите рецепты нужных библиотек в DEPENDS.
- Инструментам, работающим на сборочном компьютере, нужны соответствующие native-зависимости.
- PACKAGECONFIG и EXTRA_OECMAKE выбирают функции, поддерживаемые рецептом и версией исходников.
- Вложенные сборки должны использовать тот же compiler и sysroot устройства. Проверьте log.do_configure и CMakeCache.txt на случайные пути компьютера.
- Параметры CPU приходят из machine configuration. Аппаратным codecs нужна поддержка платформы.

FLOW-07. Собрать SDK и создать пакеты.

- Соберите SDK и проследите задачи fetch, unpack, patch, configure, compile, install и package.
- do_install пишет в ${D}, а не в /usr сборочного компьютера. При необходимости дополните установку.
- Проверьте библиотеки, подключаемые модули, ресурсы, заголовки и файлы CMake/pkg-config.
- Распределите их по пакетам через FILES. Отделите файлы разработки и отладки и исправьте ошибки упаковки QA.

```bash
bitbake linphone-sdk
```

FLOW-08. Подключить приложение.

- Рецепт phone-ui указывает рецепт SDK в DEPENDS. Заголовки, библиотеки и файлы поиска SDK становятся доступны в sysroot приложения.
- Приложение использует CMake package или pkg-config, реально предоставленные этой версией SDK. Не задавайте пути сборочного компьютера вручную.
- Зависимости shared libraries Yocto обычно определяет сам. Для plugins и данных может понадобиться RDEPENDS:${PN} с именами выходных пакетов.

```bitbake
DEPENDS += "linphone-sdk"
```

FLOW-09. Выбрать пакеты образа.

- Добавьте пакет приложения через продуктовый образ или packagegroup. В примере он называется phone-ui.
- Зависимости линковки обычно подтягивают пакеты библиотек; отдельно включите нужные plugins и ресурсы.
- Одна сборка SDK ещё не помещает его в образ.
- SDK разработки может требовать headers и другие файлы, которые не нужны в production image.

```bitbake
IMAGE_INSTALL:append = " phone-ui"
```

FLOW-10. Настроить запуск приложения.

- Если используется systemd, рецепт приложения устанавливает unit и описывает его через класс systemd.
- Выберите, нужен ли запуск при загрузке. Библиотекам SDK отдельный сервис обычно не нужен.
- Проверьте записываемые каталоги состояния и права на audio/video.
- Приложению всё равно нужны повторные попытки связи с сетью и SIP. Одного порядка запуска недостаточно для доступности внешнего сервера.

```bitbake
inherit systemd
SYSTEMD_SERVICE:${PN} = "phone-ui.service"
```

FLOW-11. Проверить образ и телефон.

- Соберите приложение, затем образ продукта. Проверьте пакеты, manifest образа и корневую файловую систему.
- Установите этот образ поддерживаемым платой способом. Проверьте архитектуру, загрузчик программ, библиотеки, подключаемые модули, сертификаты и настройки.
- На телефоне проверьте регистрацию, входящие и исходящие звонки, звук и видео, перезапуск и восстановление сети.
- Для поиска отказа используйте логи приложения и сервиса.

На сборочном компьютере:

```bash
bitbake phone-ui
bitbake phone-image
```

На устройстве:

```bash
systemctl status phone-ui.service
journalctl -u phone-ui.service
```

FLOW-12. Сделать результат повторяемым.

- Храните изменения слоёв, commits исходников, патчи и настройки функций в системе контроля версий.
- Собирайте в CI без временных подмен workspace разработчика. Сохраняйте manifests и проверяйте тот же образ на оборудовании.
- Проверьте нужную пересборку приложения после изменения SDK и соответствие установленной программы её библиотекам.
- Добавьте проверки обновления и reboot. Успешная сборка SDK — только часть поставки.

FLOW ДЛЯ УСТНОГО ОТВЕТА

Сначала я определяю конфигурацию цели и существующий provider. Затем добавляю или расширяю рецепт в продуктовом слое, фиксирую исходники, объявляю зависимости и настраиваю кросс-сборку.

BitBake собирает SDK, устанавливает результаты в staging и формирует пакеты. Приложение получает интерфейс сборки SDK через recipe sysroot.

Образ выбирает runtime-пакеты, а сервис приложения обеспечивает запуск. В конце я проверяю состав образа и на физическом устройстве тестирую звонки, media и восстановление после сбоев.

БАЗА И ПРАКТИЧЕСКИЕ УПРАЖНЕНИЯ

Poky — эталонная интеграция BitBake, метаданных OpenEmbedded-Core и конфигурации эталонного дистрибутива/BSP. OpenEmbedded предоставляет экосистему метаданных и сборки, BitBake выполняет граф задач.

Слой meta-* группирует метаданные. build/conf/bblayers.conf подключает слои, local.conf хранит локальные настройки сборки.

MACHINE выбирает оборудование/tuning, DISTRO — политику дистрибутива, рецепт образа — пакеты и image features.

DL_DIR хранит загруженные исходные данные; SSTATE_DIR — повторно используемые результаты задач, обычно в sstate-cache. Общие каталоги уменьшают повторные загрузки и сборки при совместимых конфигурациях. Изменённая signature может исключить повторное использование результата; кеши не заменяют объявленные зависимости и фиксированные исходники.

LAB-01. Загрузить базовый образ.

- Использовать поддерживаемый Linux-host и фиксированную ревизию Poky Kirkstone.
- Quick-build guide Kirkstone указывает минимум 90 GB свободного диска и 8 GB RAM; для SDK и дополнительных сборок нужен запас.
- Инициализация: source oe-init-build-env build-lab.
- В conf/local.conf задать MACHINE = "qemuarm64", выполнить bitbake core-image-minimal и runqemu qemuarm64 nographic.
- Критерий успеха — guest shell и проверка uname -a и /proc/cmdline.
- QEMU не воспроизводит все стадии загрузки физической платы.

```bash
source oe-init-build-env build-lab
```

conf/local.conf:

```bitbake
MACHINE = "qemuarm64"
```

```bash
bitbake core-image-minimal
runqemu qemuarm64 nographic
```

LAB-02. Добавить C++ приложение.

- Из build directory выполнить bitbake-layers create-layer ../meta-lab и bitbake-layers add-layer ../meta-lab.
- Создать ../hello со следующими файлами и реальной лицензией исходников; хранить исходники в системе контроля версий.

main.cpp:

```cpp
#include <iostream>
int main() { std::cout << "hello from Yocto" << std::endl; }
```

CMakeLists.txt:

```cmake
cmake_minimum_required(VERSION 3.16)
project(hello LANGUAGES CXX)
add_executable(hello main.cpp)
install(TARGETS hello RUNTIME DESTINATION bin)
```

- Выполнить devtool add hello ../hello, проверить поля исходников/лицензии и inherit cmake в сгенерированном рецепте, затем devtool build hello. Зафиксировать изменения исходников по необходимости и выполнить devtool finish hello ../meta-lab.
- Проверить экспортированный рецепт и исходники, затем выполнить bitbake hello без workspace override. Для упражнения добавить IMAGE_INSTALL:append = " hello" в local.conf, пересобрать core-image-minimal и запустить hello в QEMU.
- В продукте выбор пакетов хранится в image/packagegroup metadata.

На Linux-host сборки:

```bash
bitbake-layers create-layer ../meta-lab
bitbake-layers add-layer ../meta-lab
```

После подготовки и проверки исходников:

```bash
devtool add hello ../hello
devtool build hello
```

После фиксации изменений исходников:

```bash
devtool finish hello ../meta-lab
bitbake hello
```

conf/local.conf:

```bitbake
IMAGE_INSTALL:append = " hello"
```

```bash
bitbake core-image-minimal
runqemu qemuarm64 nographic
```

LAB-03. Экспортировать изменение ядра.

- Использовать workflow ядра из файла BSP; для упражнения QEMU выбрать linux-yocto.
- Результат — .bbappend в собственном слое, один применимый патч и фрагмент .cfg.
- После выхода из devtool workspace пересобрать ядро и образ, проверить действие патча и итоговую конфигурацию.

LAB-04. Применить overlay.

- Использовать поддерживаемую плату и соответствующий слой, например Raspberry Pi с meta-raspberrypi.
- Собрать overlay, включить в boot artifacts и настроить реальный путь загрузки на применение.
- После reboot проверить живое device tree и binding драйвера.
- Одного .dtbo в deploy directory недостаточно; BSP объясняет разные механизмы U-Boot и firmware Raspberry Pi.

РЕЛИЗНЫЕ АРТЕФАКТЫ ДЛЯ ОБНОВЛЕНИЙ С УЧЁТОМ ВЕРСИИ

- Сохраняются точные выпущенные артефакты приложения, SDK и скриптов после преобразований упаковки, а не поздняя пересборка того же source tag. Состав файлов и checksums связаны с совместимостью образа/платформы и модели.
- Пакет телефона формируется по обнаруженному исходному и целевому релизу; динамическая сборка пакета не означает перекомпиляцию для каждого телефона. Полные файлы и бинарные дельты — способы доставки в одном release contract.
- Перед дельтами проверяются исходные файлы, создаётся полный target set и сохраняется предыдущий комплект этого телефона для recovery. Ручной update.sh уже может быть частичным; новый механизм улучшает применимость и автоматизацию. Это не означает rootfs A/B или восстановление незагружающегося BSP.

РАЗДЕЛ 5. ПРЕИМУЩЕСТВА, ОГРАНИЧЕНИЯ И АЛЬТЕРНАТИВЫ

Yocto позволяет учитывать оборудование, контролировать версии и сопровождать образ длительное время. Цена — сложность метаданных, время сборки и ответственность за совместимость слоёв и обновления безопасности. Buildroot может быть проще для небольшого фиксированного образа; бинарный дистрибутив ускоряет разработку, если его пакеты и политика обновлений подходят устройству.

РАЗДЕЛ 6. ОШИБКИ И БЕЗОПАСНОСТЬ

Успешная сборка рецепта не доказывает наличие пакета в образе. Различайте DEPENDS для сборки и runtime-зависимости пакетов, host-инструменты и целевые библиотеки. Фиксируйте совместимые слои и исходники, проверяйте лицензии, защищайте ключи подписи и тестируйте обновление и откат. Использование кеша не заменяет проверку на устройстве.

РАЗДЕЛ 8. ВОПРОСЫ НА ИНТЕРВЬЮ

ВОПРОС YCT-01. Что такое слой?

Ответ: Это каталог с рецептами, дополнениями, классами и настройками одной области. conf/layer.conf описывает его содержимое, bblayers.conf подключает к сборке. Создать каталог недостаточно: слой должен быть подключён.

Пример и проверка: На телефоне поддержка платы отделяется от изменений приложения и SDK. Продуктовый слой явно подключается и объявляет зависимости. Тогда обновить vendor-слои проще без потери телефонной интеграции. При двух рецептах одного компонента проверьте итоговый выбор.

ВОПРОС YCT-02. Что делает .bbappend?

Ответ: Он дополняет подходящий рецепт: добавляет патчи, файлы, настройки или шаги сборки без копирования всего рецепта. Имя и версия должны совпасть. Применение проверяется через bitbake-layers show-appends.

Пример и проверка: Например, append продукта добавляет патч SDK без копирования vendor-рецепта. Его имя всё равно должно соответствовать выбранному рецепту. Проверьте show-appends и реальную задачу патчей. Одного файла патча в слое недостаточно.

ВОПРОС YCT-03. Почему собранного файла нет в образе?

Ответ: После компиляции файл ещё должен пройти установку, упаковку и выбор пакета в образ. Затем нужный образ должен попасть на устройство. Проверяйте эту цепочку по порядку, а не сразу пересобирайте всё.

Пример и проверка: Проследите конкретный файл, например библиотеку SDK, через установку, пакет и manifest образа. Затем сравните с файловой системой телефона. Так виден этап расхождения сборки и поставки. Пересборка библиотеки сама не добавляет пакет, который образ не выбирал.

ВОПРОС YCT-04. Для чего нужен SDK?

Ответ: Он даёт компилятор, заголовки и библиотеки для сборки программ под устройство вне полной сборки образа. Скрипт окружения выбирает правильные инструменты. SDK должен соответствовать архитектуре и библиотекам установленной системы.

Пример и проверка: При внешней сборке приложения подключите SDK environment и проверьте compiler и sysroot. Генератор, работающий на компьютере, требует исполняемого файла для компьютера. Не используйте старый desktop CMake cache. Сверьте результат с библиотеками, реально установленными на телефоне.

ВОПРОС YCT-05. Заменяет ли кеш проверку на устройстве?

Ответ: Нет. Sstate позволяет взять готовые результаты сборки с подходящими входными данными. Он не проверяет запуск, камеру, звук или GPIO. Для этого нужны отдельные проверки работающего устройства.

Пример и проверка: Неизменённый SDK может быстро восстановиться из кеша, пока другой компонент пересобирается. Это ускорение сборки, а не функциональный тест. Проверьте причины повторного использования или пересборки. Регистрацию и медиа всё равно проверяют на полученном образе независимо от cache hits.

ВОПРОС YCT-06. Чем отличаются MACHINE и DISTRO?

Ответ: MACHINE выбирает аппаратную конфигурацию и поддержку платы. DISTRO задаёт общие правила и возможности системы. Рецепт образа выбирает устанавливаемые пакеты. Это разные уровни настройки.

Пример и проверка: Представьте две модели с одной кодовой базой приложения. Настройки платы и периферия могут различаться, а правила продукта оставаться общими. Образ отдельно выбирает пакеты каждой модели. Разделите эти решения до правки local.conf ради отказа одной модели.

ВОПРОС YCT-07. Как найти пакет, содержащий файл?

Ответ: По данным уже собранных пакетов выполните oe-pkgdata-util find-path, затем list-pkg-files. Проверьте manifest образа и сам файл на устройстве. Найденный пакет ещё не означает, что его установили.

Пример и проверка: Проследите конкретный файл, например библиотеку SDK, через установку, пакет и manifest образа. Затем сравните с файловой системой телефона. Так виден этап расхождения сборки и поставки. Пересборка библиотеки сама не добавляет пакет, который образ не выбирал.

ВОПРОС YCT-08. Чем отличаются рецепт, пакет, packagegroup и образ?

Ответ: Рецепт описывает сборку компонента и может создавать несколько пакетов. Packagegroup объединяет пакеты через зависимости. Образ собирает выбранные пакеты в файловую систему и файлы для установки на устройство.

Пример и проверка: Представьте две модели с одной кодовой базой приложения. Настройки платы и периферия могут различаться, а правила продукта оставаться общими. Образ отдельно выбирает пакеты каждой модели. Разделите эти решения до правки local.conf ради отказа одной модели.

ВОПРОС YCT-09. Где хранить изменения производителя и продукта?

Ответ: Поддержку платы держат в BSP-слоях, свои приложения и дополнения — в продуктовых. Укажите зависимости и совместимость слоёв, затем проверьте выбор рецептов. Так меньше прямых правок в чужих слоях.

Пример и проверка: На телефоне поддержка платы отделяется от изменений приложения и SDK. Продуктовый слой явно подключается и объявляет зависимости. Тогда обновить vendor-слои проще без потери телефонной интеграции. При двух рецептах одного компонента проверьте итоговый выбор.

ВОПРОС YCT-10. Может ли приоритет слоя переопределить всё?

Ответ: Нет. BBFILE_PRIORITY влияет на выбор рецептов, но учитываются также версии, providers и переопределения настроек. Проверяйте выбранный рецепт и итоговые значения переменных. Не полагайтесь только на число приоритета.

Пример и проверка: Если ожидаемый рецепт SDK не выбран, проверьте версии, предпочтения providers и итоговые overrides. Приоритет слоя — лишь часть решения. После небольшой правки подтвердите реально выполняемый рецепт. Одних названий каталогов недостаточно.

ВОПРОС YCT-11. Как включить приложение и сервис в образ?

Ответ: Рецепт собирает программу и устанавливает её, настройки и unit во временную область. Файлы распределяются по пакетам, нужный пакет выбирается в образ. Затем на устройстве проверяются наличие файлов и запуск сервиса.

Пример и проверка: Для приложения телефона проверьте пакет executable и unit сервиса. Unit должен указывать установленный путь и иметь нужное правило включения. Затем загрузите образ без ручной подготовки окружения. Так проверяется весь путь установки, а не одна компиляция.

ВОПРОС YCT-12. Чем native-инструмент отличается от программы устройства?

Ответ: Native-инструмент работает на сборочном компьютере, например генерирует исходники. Целевая программа собирается для архитектуры устройства. Их нельзя смешивать: ARM-программа обычно не запустится на компьютере сборки, а его библиотеки не подходят устройству.

Пример и проверка: При внешней сборке приложения подключите SDK environment и проверьте compiler и sysroot. Генератор, работающий на компьютере, требует исполняемого файла для компьютера. Не используйте старый desktop CMake cache. Сверьте результат с библиотеками, реально установленными на телефоне.

ВОПРОС YCT-13. Зачем downloads и shared state?

Ответ: Downloads хранит загруженные исходники, shared state — готовые результаты задач. Они ускоряют разные части сборки. Даже с кешами нужно фиксировать исходники и настройки: кеш не является правилом выбора версии.

Пример и проверка: Неизменённый SDK может быстро восстановиться из кеша, пока другой компонент пересобирается. Это ускорение сборки, а не функциональный тест. Проверьте причины повторного использования или пересборки. Регистрацию и медиа всё равно проверяют на полученном образе независимо от cache hits.

ВОПРОС YCT-14. Как сделать сборку воспроизводимой?

Ответ: Зафиксируйте ревизии исходников и слоёв, инструменты, настройки и модель устройства. Исключите случайные зависимости от компьютера и скрытые загрузки. Сравнивайте результаты в одинаковых условиях. Фиксированный commit сам по себе не гарантирует побайтовое совпадение.

Пример и проверка: Старый релиз для дельты должен содержать точные поставленные файлы. Новая сборка того же tag может отличаться из-за инструментов или упаковки. Сохраняйте релизные файлы и суммы. По этим сведениям отвергайте дельту при несовпадении исходников телефона.

ВОПРОС YCT-15. Как проверить образ до установки?

Ответ: Посмотрите manifest, состав пакетов и созданную файловую систему: программы, библиотеки, units, права и настройки модели. Затем убедитесь, что устанавливается именно этот результат сборки. Успешный лог одного рецепта не описывает весь образ.

Пример и проверка: Проследите конкретный файл, например библиотеку SDK, через установку, пакет и manifest образа. Затем сравните с файловой системой телефона. Так виден этап расхождения сборки и поставки. Пересборка библиотеки сама не добавляет пакет, который образ не выбирал.

ВОПРОС YCT-16. Как безопасно уменьшить образ?

Ответ: Сначала найдите, какие пакеты и файлы занимают место. Уберите ненужные возможности и файлы разработки, сохранив рабочие зависимости, лицензии и диагностику. После изменения проверьте запуск и основные сценарии. Одного удаления symbols недостаточно.

Пример и проверка: Сначала измерьте место пакетов и файлов. Ненужный пакет разработки отличается от библиотеки обязательного codec. После изменения повторите запуск, звонки и диагностику. Также сохраняйте нужные лицензии и соответствующие symbols.

ВОПРОС YCT-17. Что проверить для rootfs только для чтения?

Ответ: Найдите все операции записи: настройки, логи, кеши, секреты и обновления. Подготовьте каталоги, доступные для записи в постоянной памяти или RAM. После перезагрузки проверьте сервисы и сохранность нужных данных.

Пример и проверка: Например, SIP-настройки должны пережить reboot, а временный кеш — не обязательно. Разместите данные в подходящих доступных для записи местах. Проверьте права пользователя сервиса. Загрузите чистую систему, чтобы каталоги случайно не остались от предыдущей сессии разработчика.

ВОПРОС YCT-18. Как планировать обновление и откат образа?

Ответ: Определите совместимый набор загрузчика, ядра, DTB, rootfs и данных. На тестовом устройстве проверьте подлинность пакета, прерванную установку и возврат к рабочему состоянию. Новая схема данных может помешать запуску старой версии.

Пример и проверка: До активации запишите точный предыдущий релиз и сохраните весь соответствующий комплект. Оставьте возможность выбрать его после отказа. Проверяйте общие настройки вместе с бинарниками. Возврат старой программы неполон, если она уже не читает необходимые данные.

ВОПРОС YCT-19. Как учитывать лицензии и исправления безопасности?

Ответ: Проверяйте лицензии компонентов и происхождение исходников, оценивайте применимость найденных уязвимостей. Исправления нужно собрать и проверить в образе. Отсутствие предупреждений сканера само по себе не доказывает безопасность продукта.

Пример и проверка: При обновлении зависимости SDK проверьте исходники и текст лицензии вместе с отчётами уязвимостей. Определите применимость к включённым функциям. Пересоберите компоненты и проверьте образ телефона. Результат сканирования нужно оценить; он не является автоматической гарантией безопасности.

ВОПРОС YCT-20. Как отделить знание Yocto от личного опыта?

Ответ: После объяснения механизма назовите свои рецепты, пакеты и изменения образа. Работа внутри готовых слоёв отличается от создания дистрибутива или BSP с нуля. Не превращайте общий технический ответ в утверждение о выполненной работе.

Пример и проверка: Полезный пример на интервью называет компонент, изменённый рецепт и проверку устройства. Добавление Linphone в готовую основу — значимая работа, но не создание всех частей BSP. Разделите командную задачу и личные изменения. Теоретическое предложение отдельно от выполненной работы.

ВОПРОС YCT-21. Чем различаются Poky, OpenEmbedded и BitBake?

Ответ: Poky — эталонный набор компонентов для начала работы. OpenEmbedded предоставляет рецепты и общую систему сборки. BitBake читает настройки и выполняет задачи. Свои слои и настройки превращают эту основу в образ продукта.

Пример и проверка: На проекте базовая поддержка платы была стартом, а не готовым телефоном. Продуктовые слои добавляли телефонию и конференции. BitBake выполнял их рецепты вместе с задачами платформы. Так видно различие общих инструментов и содержимого конкретного продукта.

ВОПРОС YCT-22. Что находится в bblayers.conf и local.conf?

Ответ: bblayers.conf подключает слои. local.conf хранит местные настройки сборки, в том числе MACHINE. MACHINE выбирает оборудование, DISTRO — правила системы, образ — устанавливаемые пакеты.

Пример и проверка: Представьте две модели с одной кодовой базой приложения. Настройки платы и периферия могут различаться, а правила продукта оставаться общими. Образ отдельно выбирает пакеты каждой модели. Разделите эти решения до правки local.conf ради отказа одной модели.

ВОПРОС YCT-23. Чем downloads отличается от sstate-cache?

Ответ: DL_DIR хранит загруженные входные файлы. SSTATE_DIR хранит результаты задач, которые можно использовать повторно при совпадении условий. Ни один кеш не исправляет отсутствующую в рецепте зависимость.

Пример и проверка: Неизменённый SDK может быстро восстановиться из кеша, пока другой компонент пересобирается. Это ускорение сборки, а не функциональный тест. Проверьте причины повторного использования или пересборки. Регистрацию и медиа всё равно проверяют на полученном образе независимо от cache hits.

ВОПРОС YCT-24. Как понять, что упражнение с рецептом выполнено?

Ответ: Рецепт собирается из своего слоя без временной подмены в workspace. Пакет указан в manifest образа, а hello запускается в пересобранной гостевой системе. Одной успешной сборки в рабочем каталоге разработчика недостаточно.

Пример и проверка: Сначала экспортируйте рецепт и изменения из workspace в основной слой. Соберите через него и проверьте manifest образа. Затем запустите приложение в пересобранной гостевой системе. Это выявит успех, зависящий только от временных файлов разработчика.

ВОПРОС YCT-25. Зачем хранить готовые релизы, а не пересобирать старый Git tag?

Ответ: Компилятор, настройки и упаковка могут изменить байты файла. Дельте нужен точный исходник с правильной контрольной суммой. Поэтому сохраняются реально поставленные файлы и сведения об их совместимости, а не только номер версии.

Пример и проверка: Старый релиз для дельты должен содержать точные поставленные файлы. Новая сборка того же tag может отличаться из-за инструментов или упаковки. Сохраняйте релизные файлы и суммы. По этим сведениям отвергайте дельту при несовпадении исходников телефона.

ВОПРОС YCT-26. Что сохранить для возврата к версии до обновления?

Ответ: Полный согласованный набор программы, библиотек, скриптов и ресурсов, их свойства и прежний выбор активного релиза. Данные должны оставаться совместимыми либо иметь способ восстановления. Одной обратной дельты или номера версии недостаточно.

Пример и проверка: До активации запишите точный предыдущий релиз и сохраните весь соответствующий комплект. Оставьте возможность выбрать его после отказа. Проверяйте общие настройки вместе с бинарниками. Возврат старой программы неполон, если она уже не читает необходимые данные.
