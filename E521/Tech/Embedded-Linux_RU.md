Embedded-Linux

РАЗДЕЛ 1. ТЕХНОЛОГИЯ И ВЕРСИЯ

Категория: Встроенная ОС

Linux на i.MX; версия ядра зависит от продукта.

РАЗДЕЛ 2. НАЗНАЧЕНИЕ

Embedded Linux — это Linux, настроенный для конкретного продукта. Кроме приложения в продукт входят ядро, драйверы, сервисы, библиотеки и настройки оборудования.

РАЗДЕЛ 3. ОСНОВНЫЕ ПОНЯТИЯ

- Ядро управляет оборудованием и предоставляет интерфейсы программам. Приложение и системные сервисы работают в пользовательской части системы.
- Загрузчик, ядро, device tree и корневая файловая система должны соответствовать плате и разметке накопителя.
- Исполняемому файлу нужны подходящие архитектура, загрузчик и библиотеки. Успешная сборка на компьютере ещё не доказывает запуск на устройстве.
- Файлы /dev, права доступа и firmware входят в поставляемую систему.
- Запуск зависит от готовности сервисов. На работу также влияют память, доступное для записи место и способы восстановления.
- На компьютере можно проверить отдельную логику. Реальные звук, камера, GPIO и работа дисплея требуют подходящего оборудования.

РАЗДЕЛ 4. ТИПИЧНОЕ ИСПОЛЬЗОВАНИЕ

Используйте dmesg для сообщений ядра, journalctl для логов сервисов при наличии, ps для процессов и ls -l /dev для устройств. Проверяйте состав образа, архитектуру программы, библиотеки, окружение сервиса, права и оборудование. При поддержке помогают удалённые gdb/gdbserver.

Если процесс работает вручную, но не при загрузке, сравните исполняемый файл, рабочий каталог, пользователя, окружение, доступные библиотеки и зависимые сервисы. При отсутствии оборудования изучите сообщения ядра и привязку драйвера до отладки приложения.

Для удалённой отладки используйте совместимые символы и фиксируйте версию установленного бинарного файла; несовпадение программы или символов может сделать стек вызовов ошибочным. Это общие приёмы диагностики, а не утверждение, что каждый случай происходил на телефоне.

ЗАГРУЗКА, КРОСС-РАЗРАБОТКА И ОБНОВЛЕНИЯ

Типичная ARM-последовательность: BootROM, необязательные SPL/early firmware, U-Boot, kernel с DTB и необязательным initramfs, затем PID 1 — systemd или sysvinit. Она зависит от SoC/boot chain. Initramfs может найти/разблокировать настоящий root и переключиться на него. Serial logs определяют первую отказавшую стадию.

Итоговая командная строка видна в /proc/cmdline. Источники могут включать U-Boot bootargs, boot configuration или chosen/bootargs в device tree; поведение CONFIG_CMDLINE зависит от архитектуры/конфигурации.

cmdline.txt у Raspberry Pi — платформенный механизм. console= выбирает консоль, root= определяет root device, rootwait ждёт его обнаружения, init= переопределяет обычный init executable, loglevel= задаёт подробность вывода в консоль.

Имена и идентификаторы зависят от платы.

Toolchain генерируется через bitbake core-image-minimal -c populate_sdk, устанавливается, затем в новом shell выполняется соответствующий environment-setup-* script. SDK с поддержкой CMake предоставляет toolchain file, обычно $OECORE_NATIVE_SYSROOT/usr/share/cmake/OEToolchainConfig.cmake.

Новый CMake build directory исключает host cache settings; проверяются compiler, sysroot и target ABI. Разработка через внешний SDK не заменяет сопровождение рецепта.

Используются gdbserver на target и соответствующий cross-GDB с теми же executable, symbols и target sysroot. strace отслеживает syscalls, perf профилирует при доступных kernel events/permissions, Valgrind диагностирует поддерживаемые сценарии памяти с накладными расходами и ограничениями архитектур. Tools/symbols добавляются в development image явно; core-image-minimal не обязан их содержать.

Userspace использует интерфейсы ядра: /dev и ioctl, sysfs, GPIO character devices через libgpiod, i2c-dev, spidev и V4L2. mmap может отображать управляемые драйвером buffers, но не отменяет ownership, cache coherence и DMA synchronization.

Где подходит, предпочтительны существующие subsystem drivers. API libgpiod зависит от версии; старый sysfs GPIO deprecated.

Права и отказы проверяются на target.

SWUpdate предоставляет настраиваемые update handlers, RAUC управляет подписанными bundles и интеграцией slots/boot, Mender сочетает обновление устройств с управлением deployments. Выбираются совместимые с продуктом релизы: текущие версии не обязательно подходят Kirkstone.

Для A/B записывается/проверяется неактивный slot, переключается boot selection, good-status ставится после health checks, число попыток ограничивается с сохранением recovery. Миграции общих данных могут мешать откату.

Read-only rootfs требует writable-каталогов state/logs. Secure boot аутентифицирует цепочку загрузки; подписи обновлений и rollback policy — отдельные меры, не автоматический результат A/B.

КОМАНДЫ КРОСС-РАЗРАБОТКИ

Генерация SDK на Linux-host сборки:

```bash
bitbake core-image-minimal -c populate_sdk
```

После установки SDK и подключения соответствующего environment-setup script, из каталога CMake-проекта:

```bash
cmake -S . -B build-target \
  -DCMAKE_TOOLCHAIN_FILE="$OECORE_NATIVE_SYSROOT/usr/share/cmake/OEToolchainConfig.cmake"
cmake --build build-target
```

Базовая диагностика на целевом устройстве:

```bash
uname -a
cat /proc/cmdline
dmesg
ls -l /dev
```

LIFETIME GPIO И ИССЛЕДОВАНИЕ ОТКАЗОВ

- Affinity QObject, выполнение worker и инициализация singleton — разные задачи. Static singleton не делает изменяемые методы thread-safe. Где возможно, аппаратные операции сериализуются одним владельцем.
- Worker в блокирующем device I/O требует timeout или явного пробуждения; QThread::quit() относится к event loop, requestInterruption() требует кооперативной проверки. Нельзя ждать завершения потока под нужным ему lock.
- Для hang собираются stacks всех потоков, определяются владельцы locks и блокирующее I/O. Для leak сравниваются контролируемые повторные циклы и данные allocations; одного роста RSS недостаточно.

Команды сессии GDB:

```text
info threads
thread apply all bt
```

РАЗДЕЛ 5. ПРЕИМУЩЕСТВА, ОГРАНИЧЕНИЯ И АЛЬТЕРНАТИВЫ

Linux даёт зрелую экосистему и сеть, но размер и обычное планирование могут не подойти маленькому устройству или системе с жёстким real time. RTOS подходит для строгих сроков и малого объёма. PREEMPT_RT и оборудование нужно оценивать отдельно: гарантии жёсткого real time нельзя предполагать.

РАЗДЕЛ 6. ОШИБКИ И БЕЗОПАСНОСТЬ

Отсутствующий драйвер, неверный device tree, недостающий firmware и права могут выглядеть как ошибка приложения. Износ накопителя, потеря питания при обновлении, сети и памяти влияют на надёжность. Применяйте минимальные права, защищайте учётные данные и воспроизводите проблему на устройстве, если важны периферия или время.

РАЗДЕЛ 8. ВОПРОСЫ НА ИНТЕРВЬЮ

ВОПРОС EL-01. Что делает PID 1?

Ответ: Это первый процесс пользовательской части системы. У него особые обязанности, в том числе обработка завершившихся осиротевших процессов. Обычно init-система запускает сервисы и управляет выключением. Работающий PID 1 не означает готовность всех сервисов.

ВОПРОС EL-02. Что такое корневая файловая система?

Ответ: Это файловая система, смонтированная как /. В ней находятся программы, библиотеки и настройки. Отдельные каталоги могут размещаться в постоянной памяти или RAM. Нужно заранее определить, куда приложения смогут писать.

ВОПРОС EL-03. Зачем нужен device tree?

Ответ: Он описывает оборудование, которое система не может полностью обнаружить сама: подключения, адреса, прерывания и другие ресурсы. Он не заменяет драйвер. Описание, драйвер и реальная плата должны соответствовать друг другу.

ВОПРОС EL-04. Гарантирует ли Linux выполнение в жёсткие сроки?

Ответ: Обычная конфигурация — нет. На задержки влияют планировщик, прерывания, драйверы и нагрузка. Для требований реального времени проверяют худший случай под нагрузкой, а не только среднюю задержку.

ВОПРОС EL-05. Почему нужна проверка на устройстве?

Ответ: Там реальные драйверы, загрузка, периферия и ограничения ресурсов. Тест на компьютере полезен для логики, но не доказывает работу камеры, GPIO, звука и запуска телефона. Нужны оба уровня проверки.

ВОПРОС EL-06. Почему приложение работает из shell, но не как сервис?

Ответ: Могут отличаться пользователь, группы, переменные окружения, рабочий каталог, ограничения и готовность зависимостей. Сравните эти условия и журналы. В ручном запуске сервисы уже могут быть готовы, хотя при загрузке это ещё не так.

ВОПРОС EL-07. Что нужно для правильного удалённого стека вызовов?

Ответ: Точный исполняемый файл и symbols установленной версии, подходящие архитектура и отладчик. Библиотеки должны соответствовать нужному sysroot. Стек от другой сборки может выглядеть правдоподобно и при этом вводить в заблуждение.

ВОПРОС EL-08. Как обычно загружается embedded Linux?

Ответ: Boot ROM и начальные загрузочные компоненты запускают загрузчик. Он передаёт управление ядру с описанием оборудования. Ядро подготавливает систему и запускает пользовательскую часть, иногда через initramfs. Точные этапы зависят от платы.

ВОПРОС EL-09. Почему файл существует, но возникает Exec format error или No such file?

Ответ: Возможны неверная архитектура, отсутствующий ELF-загрузчик или интерпретатор скрипта. Проверьте тип файла, путь интерпретатора и зависимости. Сообщение об отсутствии файла не всегда относится к самому запускаемому файлу.

ВОПРОС EL-10. Как найти отсутствующую shared library?

Ответ: Проверьте, какие библиотеки требует программа, есть ли они на устройстве и где их ищет загрузчик. Сопоставьте версии и ABI. На компьютере исследуйте ELF подходящими инструментами, а запуск проверяйте в среде устройства.

ВОПРОС EL-11. Что общего у потоков одного процесса?

Ответ: Они используют общее адресное пространство и многие ресурсы процесса. У каждого потока свои стек и регистры. Общие данные требуют синхронизации, а отдельные процессы обычно имеют изолированную память.

ВОПРОС EL-12. Как отличить deadlock от медленной работы?

Ответ: Посмотрите стеки всех потоков и повторите наблюдение. Ищите цикл ожидания блокировок либо длительную операцию ввода-вывода. Зависший интерфейс сам по себе не доказывает deadlock.

ВОПРОС EL-13. Как правильно остановить рабочий поток?

Ответ: Передайте запрос остановки и обеспечьте выход из ожидания: таймаутом или пробуждением. Дождитесь завершения и затем освободите ресурсы. Нельзя ждать поток, удерживая mutex, который нужен ему для выхода.

ВОПРОС EL-14. Что важно при работе QThread с GPIO?

Ответ: Определите, в каком потоке живут QObject и кто владеет аппаратными ресурсами. Не обновляйте UI из рабочего потока. Блокирующее ожидание должно прерываться; один quit() не остановит произвольный цикл чтения GPIO.

ВОПРОС EL-15. Как обрабатывать дребезг GPIO?

Ответ: Сначала определите реальное поведение сигнала и полярность. Отделите электрические фронты от подтверждённого состояния трубки. При необходимости примените фильтрацию и проверьте быстрые переключения, чтобы не терять настоящие действия пользователя.

ВОПРОС EL-16. Доказывает ли рост RSS утечку памяти?

Ответ: Нет. Память могут занимать кеши, отображённые файлы и временные буферы. Повторяйте одинаковые операции и исследуйте выделения и освобождения памяти. Утечка означает, что память не освобождена после завершения её полезного использования.

ВОПРОС EL-17. Как сохранять настройки при риске отключения питания?

Ответ: Нужно исключить использование наполовину записанного файла. Частый подход — полностью записать временный файл, синхронизировать данные и заменить основной файл. Для сохранности может потребоваться синхронизация каталога. Проверяйте отключением питания: одного close недостаточно.

ВОПРОС EL-18. Что меняется при rootfs только для чтения?

Ответ: Найдите все места записи: настройки, логи, кеши и сведения обновления. Разместите их в подходящих записываемых каталогах с нужными правами. Отдельно проверьте, что должно пережить перезагрузку, а что можно хранить в RAM.

ВОПРОС EL-19. Как исследовать ошибку доступа без постоянного запуска от root?

Ответ: Проверьте пользователя, группы, права файлов и устройств, а также ограничения сервиса. Дайте только доступ, необходимый операции. Запуск от root может помочь проверить гипотезу, но не объясняет и не исправляет исходные права.

ВОПРОС EL-20. Что проверять модульными, интеграционными и аппаратными тестами?

Ответ: Модульные тесты проверяют отдельные правила и переходы состояния. Интеграционные — взаимодействие компонентов. Загрузка, GPIO, камера, звук и содержимое образа требуют проверки в подходящей системе или на оборудовании. Один уровень не заменяет другие.

ВОПРОС EL-21. Исправляет ли rootwait ошибку корневой файловой системы?

Ответ: Он ждёт появления устройства. Он не исправит неверный раздел, отсутствующий драйвер или неподдерживаемую файловую систему. Сначала найдите отказавший этап и проверьте root=.

ВОПРОС EL-22. Почему программа из SDK не запускается на устройстве?

Ответ: Могут различаться архитектура, загрузчик, libc, C++ ABI или библиотеки. Используйте окружение соответствующего SDK и новый каталог сборки CMake. Проверьте реальные зависимости программы.

ВОПРОС EL-23. Когда выбирать strace, perf, Valgrind и GDB?

Ответ: strace показывает системные вызовы, perf помогает найти затраты процессора, Valgrind исследует ошибки памяти, GDB — состояние и выполнение программы. У инструментов разные требования, ограничения архитектур и накладные расходы.

ВОПРОС EL-24. Гарантируют ли A/B-разделы безопасное обновление и откат?

Ответ: Нет. Нужны проверка пакета, правильный выбор загрузки, ограничение попыток и подтверждение работоспособности. Миграция данных или запрет возврата на старую версию могут помешать откату. Secure boot требует отдельной цепочки доверия.

ВОПРОС EL-25. Достаточно ли безопасно создать singleton для потокобезопасного GPIO?

Ответ: Нет. Создание объекта, его QObject affinity, доступ к данным и уничтожение — разные задачи. Один владелец GPIO с очередью команд может упростить работу. Но его поток должен уметь принимать команды и завершаться.

ВОПРОС EL-26. Как исследовать deadlock и утечку в GPIO-слое?

Ответ: Для deadlock нужны стеки потоков и понимание, кто какой lock удерживает и ждёт. Для утечки — данные о выделении и времени жизни памяти при повторных операциях. Отдельно проверяются файловые дескрипторы и запросы GPIO. Одного RSS или зависшего UI недостаточно.
